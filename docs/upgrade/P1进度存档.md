## 四、表结构现状（0004）

- `jobs`：九状态 CHECK；`pending_action` 只允许 `pause` / `cancel` 或空；`idempotency_key` 唯一；`retry_of_job_id` 与 `resume_of_job_id` 自引用；任务级租约字段 `lease_owner` / `lease_expires_at` 由 P1-05 写入，认领时随 running 一起落库。
- `uniq_active_fingerprint`：`(ticker_code, analysis_date, config_hash)` 的部分唯一索引，只对五个活动状态生效。契约第 4 节的 20 并发裁决靠它兜底，不要改成应用层先查后插。
- `job_stages`：主键 `(job_id, stage_id)`；`stage_id` 固定 12 个、状态五态，均有 CHECK；FK 级联删除。P1-07 起由 Worker 逐阶段写入 `status` / `started_at` / `ended_at` / `report_path`，`report_path` 是相对报告根目录的路径。
- `job_events`：自增 `id`，`UNIQUE(job_id, seq)`，`seq >= 1`；审计记录 `created` / `transition_rejected` / `reconcile_note` 的 `seq` 为 NULL，可重复，不占事件流序号；`snapshot` 不写入事件表。P1-07 起 T02 认领也写 `status_changed`，作为 seq 1。
- `job_idempotency_keys`（0003）：`idempotency_key` 主键、`job_id` 外键级联、`body_hash`、`created_at`。`jobs.idempotency_key` 只记创建它的那把键；第 3 步用新键复用活动任务时，绑定写在这张表，保证同一把键再提交异体时按第 2 步报 409，而不是落到第 4 步。
- `worker_lease`（0004）：单行表，`CHECK (id = 1)`，迁移时播种 `(1, NULL, NULL, NULL)`。`owner` 为空或 `expires_at` 已过即可被接管；接管、续期、释放都按 (owner, expires_at) 做 CAS，不删行重建。
- `job_kernel_meta`（0001）：`schema_contract = p0-contracts-v1`。

## 七、P1-02 至 P1-07 留下的注意事项

- 迁移头前移时，P1-01 里断言"head 建出哪些表"的测试必须同步更新，否则正常的迁移演进会被误判为回归。DB-01、DB-03 已改为断言 0002 的 5 张表，DB-03 仍验证 downgrade base 无残留。
- `jobs` 表没有统计四字段与报告行，这是刻意的：统计走 `job_events`，最终报告行在 P1-09 加，各自带迁移。不要在 P1-02 或 P1-07 预埋。
- P1-03 的配置哈希要覆盖模型配置、阶段开关与图版本；`config_snapshot` 存完整规范化配置，`config_hash` 只存哈希，两者都不允许后续原地修改。
- `config_hash` 已把 `graph_version` 纳入哈希（契约定义）。API 的 `config_digest` 就是库里的 `config_hash`，P1-04 直接取用，不要另算第二套。
- 阶段开关的允许键来自服务端 meta/options 配置，由调用方以 `defaults` 传入 `normalize_config`。代码里不硬编码 `policy` / `hot_money` / `lockup`。
- 配置异常到错误码是固定映射，P1-04 不要再发明新码：`UnknownConfigKey` → 422 `config_unknown_key`，`InvalidConfigValue` → 422 `config_invalid_value`，`ResumeFingerprintMismatch` → 409 `resume_fingerprint_mismatch`。
- P1-04 的创建路径只有 `JobService.create_job` 一条。P1-05 Worker 只认领已存在的 queued 行，不得复制一份创建逻辑，也不得改 `config_hash` / `config_snapshot` / `idempotency_*` 字段。
- 读判定存在快照竞态：同配置任务可能在「查同指纹」与「查同票同日」两条 SELECT 之间提交。P1-04 在冲突分支再比一次 `config_hash`，相等仍按第 3 步复用；不要删掉这个判断，并发测试会立刻变红。
- 未知顶层请求字段目前返回 422 `invalid_request`。api-v1 第 0 节要求 422，但 error-codes-v1 给 `invalid_request` 定的是 400，且没有专用码。这是契约空白，P1-04 按通则的 422 实现；要改先走 `FREEZE-v1.md` 第 4 节。
- `JobDetail.stages` 已由 P1-07 改为读 `job_stages` 真实行，不要再在 serializer 里合成阶段。新建任务没有阶段行时仍显示 12 个 pending，这是同一投影的默认值。
- `create_app()` 是工厂，模块级不建 app、不建引擎，避免导入时创建默认数据目录。P1-11 加 SSE 路由时继续用 `create_app` 注入，不要在模块顶层 new 引擎。
- `worker_lease` 只有一行，迁移播种后永不删除。接管判断是「`owner` 为空或 `expires_at` 已过」，续期与释放只对当前 owner 生效；不要改成先查后无条件更新，第二个 Worker 会短暂并行。
- 租约时间戳用毫秒格式，任务与事件时间戳用秒。短 TTL 测试（200ms）依赖毫秒精度，不要为了统一把租约改成秒。
- 默认 TTL 30 秒、心跳间隔 10 秒。测试通过 `LeaseService(clock=..., ttl=...)` 与 `Worker(heartbeat_interval=...)` 注入短值，不要改默认常量去迁就测试。
- running 行的任务租约过期后不会自动重认领，状态保持 running，由 P1-10 启动对账转 interrupted 并写 `reconcile_note`。不要在 claim 路径加「过期即重跑」。
- 心跳失败或租约被他人接管时 `Worker.lost` 置位，`claim()` 随即返回 None。P1-08 的执行循环要在每个阶段边界检查这个标志，再决定是否继续写产物；目前 `run_once` 仍是一次调用跑完 12 阶段。
- `Worker.shutdown()` 先停心跳再释放租约，且只释放自己持有的；不要反过来，否则释放与续期会互相覆盖。
- 执行器工厂在 `backend/app/services/analysis_runner.py`。默认 `FakeAnalysisExecutor` 惰性导入 `tests.fake_analysis_graph.py`，所以必须在仓库根目录运行（`tests` 按命名空间包解析）；不要复制假图的 STAGES、流或报告逻辑到 backend。
- 假图阶段目录与 `backend/app/models/stage.py` 的 `STAGE_IDS` 不一致时抛 `stage_catalog_mismatch`，先修契约或假图，不要放宽检查。
- AD-01 双条件：环境变量 `TA_ENABLE_REAL_RUNNER=1` 且 `ServerConfig.real_runner_enabled=True`。P1 没有真实适配器，双条件成立时工厂抛 `real_runner_unavailable`，这是有意的 fail-fast，不允许静默退回假图；P6 接真实执行器时再改这里。
- 假图统计里的 `elapsed_ms` 是 12 阶段各 30 分钟的虚拟值（21600000），只能用于和 S00 对账，不能当性能数据。
- `Worker(lease, jobs=..., reports=...)` 的 `jobs` 与 `reports` 是必填参数，P1-11 的进程入口必须把与 API 相同的 `ReportStore` 传进来。不要给 Worker 加一个「不落库」的默认模式，否则产品路径会静默丢阶段。
- `Worker.run_once()` 现在是「认领 + 执行 + 逐阶段落库 + 第 13 条 stats」，但**不写终态**。succeeded / failed 与 `report_ready` 归 P1-09，不要在 Worker 里提前写。
- 事件追加只有一个入口：`backend/app/services/event_log.py::append_event`。广播事件取 `MAX(seq)+1`，审计事件必须传 `broadcast=False`；不要在别处自己算 seq，否则补发会出现空洞或重复。
- T02 的 `status_changed` 与认领 UPDATE 在同一事务提交，它是每个任务事件流的 seq 1。不要再在 Worker 里补发一次 queued→running。
- 每个阶段固定三件事：`stage_changed(started)`、报告文件、`done` + `stats`。提交顺序是 started → 文件 → done → stats；不要先写 done 事件再写文件，否则崩溃窗口会变成「有完成事件、没产物」，落进 B4 语义。
- 统计事件是「12 个阶段各一条 + 终态前一条」，共 13 条。阶段条记录累计值；第 13 条由 `run_once` 在终态转换前写，P1-09 只补 `status_changed` 与 `report_ready`，不要再补第四条统计。
- 阶段报告根目录由 `TA_JOB_REPORTS_DIR` 指定，默认 `~/.tradingagents/job_reports`。它故意不复用旧版 `~/.tradingagents/logs`；不要把阶段报告写进旧目录，也不要让旧版读取新目录。
- 库内只存阶段报告相对路径（`<job>/<stage>/attempt-<n>.md`）。读取必须走 `ReportStore.read_stage_report` 的根目录校验；不要把绝对路径写进 `job_stages.report_path`。
- 同一阶段重复写入生成 `attempt-2.md`、`attempt-3.md`，永不覆盖旧文件。续跑、重试与测试清理都不要删旧 attempt；B3 对账依赖磁盘产物作为证据。
- 阶段报告截断按字节算 128 KiB，`full_length` 是原文字符数；截断后按 UTF-8 边界解码，不产生替换字符。不要改成按字符截断，契约单位是 KiB。
- B3 检测在 P1-07 只做到「文件存在 + 阶段仍 active + 无 done 事件 → 返回对账备注」。把任务改判 interrupted、把备注写进审计表并决定续跑起点是 P1-10 的事；不要在检测函数里改状态。
- `reconcile_note` 的 `seq` 必须是 NULL，只进 `JobDetail.reconcile_notes`，不进 SSE。P1-07 的 GF-13 已验证事件流仍为 1..8 无空洞。
- SM-03 在 P1-07 只覆盖阶段报告：12 个阶段文件与假图输出逐字相等。最终 ReportDTO 行、`content_hash` 与 `report_id` 仍在 P1-09 落库，不要提前建 reports 表。
- 阶段报告 GET（1.10）只对 `done` / `failed` 且 `report_path` 非空时读文件；`pending` / `active` / `skipped` 返回 200 + `markdown: null`。路由只读：不触发对账、不改状态、不发事件。
- `current_stage` 取第一个 `active` 阶段，`queued` 与四个终态固定为 null。`paused` 下的阶段状态语义由 P1-08 决定，当前投影不额外推断。

- 执行器可注入 `Worker(executor=...)`，测试与后续持久化包装用它；生产走工厂默认值，不要在 Worker 里另建第二套选择逻辑。
