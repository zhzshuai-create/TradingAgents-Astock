## 四、表结构现状（0005）

- `jobs`：九状态 CHECK；`pending_action` 只允许 `pause` / `cancel` 或空；`idempotency_key` 唯一；`retry_of_job_id` 与 `resume_of_job_id` 自引用；任务级租约字段 `lease_owner` / `lease_expires_at` 由 P1-05 写入，认领时随 running 一起落库。
- `uniq_active_fingerprint`：`(ticker_code, analysis_date, config_hash)` 的部分唯一索引，只对五个活动状态生效。契约第 4 节的 20 并发裁决靠它兜底，不要改成应用层先查后插。
- `job_stages`：主键 `(job_id, stage_id)`；`stage_id` 固定 12 个、状态五态，均有 CHECK；FK 级联删除。P1-07 起由 Worker 逐阶段写入 `status` / `started_at` / `ended_at` / `report_path`，`report_path` 是相对报告根目录的路径。
- `job_events`：自增 `id`，`UNIQUE(job_id, seq)`，`seq >= 1`；审计记录 `created` / `transition_rejected` / `reconcile_note` 的 `seq` 为 NULL，可重复，不占事件流序号；`snapshot` 不写入事件表。P1-07 起 T02 认领也写 `status_changed`，作为 seq 1。
- `job_idempotency_keys`（0003）：`idempotency_key` 主键、`job_id` 外键级联、`body_hash`、`created_at`。`jobs.idempotency_key` 只记创建它的那把键；第 3 步用新键复用活动任务时，绑定写在这张表，保证同一把键再提交异体时按第 2 步报 409，而不是落到第 4 步。
- `worker_lease`（0004）：单行表，`CHECK (id = 1)`，迁移时播种 `(1, NULL, NULL, NULL)`。`owner` 为空或 `expires_at` 已过即可被接管；接管、续期、释放都按 (owner, expires_at) 做 CAS，不删行重建。
- `reports`（0005）：report-schema-v1 的不可变报告行。`report_id` 主键；`job_id` 外键 `ON DELETE SET NULL` 且 `uq_reports_job_id` 唯一，让「一任务一报告」成为数据库事实；`payload` 存全文，标量列（ticker、rating、signal、content_hash、data_quality_status、chart_snapshot_status 等）供列表过滤与 report_ready 载荷；枚举列全部带 CHECK；索引 `ix_reports_ticker_date`。报告行只随终态事务插入，永不更新。
- `job_kernel_meta`（0001）：`schema_contract = p0-contracts-v1`。

- 接受控制返回 202 `{job_id, accepted:true, action, accepted_at, expected_effect:"at_stage_boundary", status}`；重复请求返回 200 `{accepted:false, reason:"already_pending", status}`，只在 pause 对 `pause_requested`、cancel 对 `cancel_requested` 时成立；其余非法组合一律 409 `illegal_transition`，details 固定 `{from, action, rule}`（rule 可为 null）。`expected_effect` 三种动作都用 `at_stage_boundary`，这是冻结契约 1.6 的固定值，不要按动作另造字符串。
- 非法动作在 service 里追加一条 `transition_rejected` 审计（`broadcast=False`，seq 为 NULL）后再抛 409；路由只负责把 `JobControlError` 转成 `ApiError`。不要在路由层补审计，否则一次请求会写两条。
- `allowed_actions` 的唯一实现在 JobDetail serializer 的九状态表：queued `[cancel]`、running `[pause,cancel]`、pause_requested `[cancel]`、paused `[resume,cancel]`、cancel_requested `[]`、cancelled `[reanalyze]`、succeeded/failed `[retry,reanalyze]`、interrupted `[resume_from_checkpoint,retry,reanalyze]`。P1-09 加 retry 时改这张表，不要在路由另算。
- T09 与 T10 靠 `_worker_idle` 区分：读全局 `worker_lease` 行，要求 owner 未过期，且该 owner 名下没有 `running` / `pause_requested` / `cancel_requested` 任务；没有活租约视为空闲。测试里模拟「Worker 忙」必须先真拿一把租约并挂一个 running 任务，不要只改状态糊弄判断。
- 认领优先级固定为 control → resumed → queued。`claim_control_job`（cancel_requested 且无租约）与 `claim_resumed_job`（running 且无租约）只挂租约、不写状态事件；T09 的 `status_changed(running)` 在 resume 时已经写过，不要再补 queued→running。
- resume 前必须重算指纹：`graph_version` 相等且 `config_hash(config_snapshot, graph_version)` 等于库里的 `config_hash`，否则 409 `resume_fingerprint_mismatch`。`config_snapshot` 与 `config_hash` 仍然只读，恢复不得改写。
- pause 落地时清 `pending_action` 与任务租约，并写 `resume_from_stage=首个未完成阶段`；resume 使用该检查点起跑。不要用「阶段计数」或「当前时间」推续跑点。
- 恢复运行的累计统计从库中最新 stats 续接，`run_once` 终态写的是 `cumulative` 而不是 `result.stats`（后者只覆盖剩余阶段）。不要改回 `result.stats`，SM-07 的 13 条累计对账会立刻变红。
- 假图执行器从 `resume_from_stage` 索引开始，前缀阶段静默消费（不触发 `on_stage` / `on_chunk` / stats），已完成阶段行保持 `done`。未知阶段抛 `resume_stage_unknown`；不要改成重置阶段行或补发事件。
- 取消的终态写法分两类：queued 直接取消写一条零值 stats（seq 1）再写 `cancelled`（seq 2）；running / pause_requested / paused 在边界写累计 stats 再写 `cancelled`。P1-09 的 succeeded 只补一条终态前 stats，不要给 cancelled 再加第三条。
- 迟到判断在执行器返回后：状态仍是 `pause_requested` / `cancel_requested` 时置 succeeded，`status_changed.detail` 记 `pause_noop` / `cancel_noop`。P1-09 起这条路径也提交报告与 `report_ready`（SM-10 断言事件流末三条为 stats、status_changed、report_ready）。
- `Worker.run_once()` 返回 `WorkerOutcome(job, result, stopped)`，`stopped` 取 `cancelled` / `paused` / `lost` 或空；既有测试读 `outcome.job` / `outcome.result`，新增测试照此写，不要退回裸 `RunResult`。
- 控制动作的 `accepted_at` 用服务端时钟秒级，与任务时间戳同格式；不要用租约的毫秒格式。
- 终态写入只有一个入口：`JobService.finish_success` / `finish_failure`。两者都用条件 UPDATE（`WHERE id=? AND status IN (running, pause_requested, cancel_requested)`）判定赢家；rowcount=0 即输家，不写事件、不写报告。不要在 Worker 里先查状态再改，检查与写入必须是同一条 UPDATE。
- 成功事务的事件顺序固定：stats → status_changed(succeeded) → report_ready。`report_ready` 只在报告行同事务插入时追加，载荷 `{report_id, content_hash, rating, signal, url}`；不要先发事件后写报告，B5 靠这一条同事务消除。
- `report_document.finalize_report` 是报告字段的权威来源：job 元数据、`generated_at_source=job_clock`、`origin=new`、`schema_version=report-v1`、rating→signal 映射、data_quality_status / chart_snapshot_status 枚举兜底、`content_hash` 全部由服务端算；执行器 meta 里的同名字段会被覆盖，只有它提供的 `report_id` 会被保留。
- `content_hash` 只覆盖 `sections`：UTF-8、`ensure_ascii=False`、`sort_keys=True`、紧凑分隔符的 sha256。改字段或改分隔符都会改变黄金哈希，动之前先判断是不是契约变更。
- 失败终态把仍在 active 的阶段标 failed 并发 `stage_changed(failed)`；阶段后异常没有 active 阶段时，`status_changed.detail` 记 `post_stage_error`，不要凭空造一条失败阶段。
- 重试 `POST /api/v1/jobs/{job_id}/retry` 的幂等体哈希是 `sha256(canonical_json({job_id, mode}))`，与创建路径的 body_hash 不共享命名空间；同一把键先 replay 再看任务状态，和 1.3 的五步顺序一致。
- `same_config` 复制原 `config_snapshot` 并按当前 `graph_version` 重算 `config_hash`；`resume_from_checkpoint` 仅限 interrupted 且指纹一致，起点是第一个未完成阶段。原任务的任何列都不被重试修改。
- 重试出的新任务带 `retry_of_job_id` 溯源，不参与活动指纹，因此可与原任务并存；失败后再次重试会生成第三个任务，报告行的 `retry_of_job_id` 记录直接的溯源边。
- ID-09（PDF 缓存命中不重渲染）依赖 P3 的导出端点与渲染器，P1 不预埋。
- B5 的恢复分支（外部已置 succeeded 但缺 report_ready 或缺报告行）由 P1-10 对账处理；正常路径已在 P1-09 同事务消除，P1-10 不要再重写一遍正常终态。
