### 1.1 现在能跑通的路径

一句话：从建任务到崩机恢复的主线已经闭合，只差事件流。

1. 建任务：`POST /api/v1/jobs` 带幂等键，五步裁决后落一条 queued 任务与 12 条 pending 阶段；同指纹同配置复用原任务，异配置 409。
2. 执行：Worker 取得单行租约后先跑启动对账，再按 control → resumed → queued 认领；假图逐阶段产出，每阶段固定写 started 事件、报告文件、done 事件与累计统计。
3. 控制：暂停 / 恢复 / 取消只登记请求，在阶段边界落地；暂停写检查点，恢复从检查点起跑，取消写累计统计后进 cancelled。
4. 终态：成功在同一条事务里写最终统计、succeeded 与 report_ready，并在提交前落 `<job>/report.json`；失败写错误码并把 active 阶段标 failed；重试创建新任务并带 `retry_of_job_id`。
5. 崩溃：重启对账把没有活租约的 running / pause_requested / cancel_requested / paused 转 interrupted，B3/B4 落审计备注，B5 只补一条 report_ready，绝不自动重跑。
6. 读接口：`GET /api/v1/jobs/{id}` 与 `GET /api/v1/jobs/{id}/stages/{stage_id}` 已可用；`GET .../events` 是 P1-11 的事。

## 四、表结构现状（0005）

- `jobs`：九状态 CHECK；`pending_action` 只允许 `pause` / `cancel` 或空；`idempotency_key` 唯一；`retry_of_job_id` 与 `resume_of_job_id` 自引用；任务级租约字段 `lease_owner` / `lease_expires_at` 由 P1-05 写入，认领时随 running 一起落库。
- `uniq_active_fingerprint`：`(ticker_code, analysis_date, config_hash)` 的部分唯一索引，只对五个活动状态生效。契约第 4 节的 20 并发裁决靠它兜底，不要改成应用层先查后插。
- `job_stages`：主键 `(job_id, stage_id)`；`stage_id` 固定 12 个、状态五态，均有 CHECK；FK 级联删除。P1-07 起由 Worker 逐阶段写入 `status` / `started_at` / `ended_at` / `report_path`，`report_path` 是相对报告根目录的路径。
- `job_events`：自增 `id`，`UNIQUE(job_id, seq)`，`seq >= 1`；审计记录 `created` / `transition_rejected` / `reconcile_note` 的 `seq` 为 NULL，可重复，不占事件流序号；`snapshot` 不写入事件表。P1-07 起 T02 认领也写 `status_changed`，作为 seq 1。
- `job_idempotency_keys`（0003）：`idempotency_key` 主键、`job_id` 外键级联、`body_hash`、`created_at`。`jobs.idempotency_key` 只记创建它的那把键；第 3 步用新键复用活动任务时，绑定写在这张表，保证同一把键再提交异体时按第 2 步报 409，而不是落到第 4 步。
- `worker_lease`（0004）：单行表，`CHECK (id = 1)`，迁移时播种 `(1, NULL, NULL, NULL)`。`owner` 为空或 `expires_at` 已过即可被接管；接管、续期、释放都按 (owner, expires_at) 做 CAS，不删行重建。
- `reports`（0005）：report-schema-v1 的不可变报告行。`report_id` 主键；`job_id` 外键 `ON DELETE SET NULL` 且 `uq_reports_job_id` 唯一，让「一任务一报告」成为数据库事实；`payload` 存全文，标量列（ticker、rating、signal、content_hash、data_quality_status、chart_snapshot_status 等）供列表过滤与 report_ready 载荷；枚举列全部带 CHECK；索引 `ix_reports_ticker_date`。报告行只随终态事务插入，永不更新。
- 报告文件不在库内：阶段报告为 `<job>/<stage>/attempt-<n>.md`，最终报告为 `<job>/report.json`（P1-10 在终态提交前写入，仅作 B4 证据，对账不导入）。
- `job_kernel_meta`（0001）：`schema_contract = p0-contracts-v1`。

## 七、P1-02 至 P1-10 留下的注意事项

- 迁移头前移时，P1-01 里断言"head 建出哪些表"的测试必须同步更新，否则正常的迁移演进会被误判为回归。DB-01、DB-03 已改为断言 0002 的 5 张表，DB-03 仍验证 downgrade base 无残留。

- P1-03 的配置哈希要覆盖模型配置、阶段开关与图版本；`config_snapshot` 存完整规范化配置，`config_hash` 只存哈希，两者都不允许后续原地修改。
- `config_hash` 已把 `graph_version` 纳入哈希（契约定义）。API 的 `config_digest` 就是库里的 `config_hash`，P1-04 直接取用，不要另算第二套。
- 阶段开关的允许键来自服务端 meta/options 配置，由调用方以 `defaults` 传入 `normalize_config`。代码里不硬编码 `policy` / `hot_money` / `lockup`。
- 配置异常到错误码是固定映射，P1-04 不要再发明新码：`UnknownConfigKey` → 422 `config_unknown_key`，`InvalidConfigValue` → 422 `config_invalid_value`，`ResumeFingerprintMismatch` → 409 `resume_fingerprint_mismatch`。
- P1-04 的创建路径只有 `JobService.create_job` 一条。P1-05 Worker 只认领已存在的 queued 行，不得复制一份创建逻辑，也不得改 `config_hash` / `config_snapshot` / `idempotency_*` 字段。
- 读判定存在快照竞态：同配置任务可能在「查同指纹」与「查同票同日」两条 SELECT 之间提交。P1-04 在冲突分支再比一次 `config_hash`，相等仍按第 3 步复用；不要删掉这个判断，并发测试会立刻变红。
- 未知顶层请求字段目前返回 422 `invalid_request`。api-v1 第 0 节要求 422，但 error-codes-v1 给 `invalid_request` 定的是 400，且没有专用码。这是契约空白，P1-04 按通则的 422 实现；要改先走 `FREEZE-v1.md` 第 4 节。
- `JobDetail.stages` 已由 P1-07 改为读 `job_stages` 真实行，不要再在 serializer 里合成阶段。新建任务没有阶段行时仍显示 12 个 pending，这是同一投影的默认值。
- `create_app()` 是工厂，模块级不建 app、不建引擎，避免导入时创建默认数据目录。P1-11 加 SSE 路由时继续用 `create_app` 注入，不要在模块顶层 new 引擎。
- `worker_lease` 只有一行，迁移播种后永不删除。接管判断是「`owner` 为空或 `expires_at` 已过」，续期与释放只对当前 owner 生效；不要改成先查后无条件更新，第二个 Worker 会短暂并行。
- 租约时间戳用毫秒格式，任务与事件时间戳用秒。短 TTL 测试（200ms）依赖毫秒精度，不要为了统一把租约改成秒。
- 默认 TTL 30 秒、心跳间隔 10 秒。测试通过 `LeaseService(clock=..., ttl=...)` 与 `Worker(heartbeat_interval=...)` 注入短值，不要改默认常量去迁就测试。
- running 行的任务租约过期后不会自动重认领，状态保持 running，由 P1-10 启动对账转 interrupted（`lease_expired`）；`reconcile_note` 只在 B3/B4 有未登记产物时追加。不要在 claim 路径加「过期即重跑」。

- `Worker.shutdown()` 先停心跳再释放租约，且只释放自己持有的；不要反过来，否则释放与续期会互相覆盖。

- T02 的 `status_changed` 与认领 UPDATE 在同一事务提交，它是每个任务事件流的 seq 1。不要再在 Worker 里补发一次 queued→running。
- 每个阶段固定三件事：`stage_changed(started)`、报告文件、`done` + `stats`。提交顺序是 started → 文件 → done → stats；不要先写 done 事件再写文件，否则崩溃窗口会变成「有完成事件、没产物」，落进 B4 语义。
- 统计事件是「12 个阶段各一条 + 终态前一条」，共 13 条。阶段条记录累计值；第 13 条由 `finish_success` / `finish_failure` 与终态事件同事务写入，`run_once` 不再单独 `record_stats`。取消路径仍只有一条零值或累计 stats，不要给终态再加第四条。
- 阶段报告根目录由 `TA_JOB_REPORTS_DIR` 指定，默认 `~/.tradingagents/job_reports`。它故意不复用旧版 `~/.tradingagents/logs`；不要把阶段报告写进旧目录，也不要让旧版读取新目录。
- 库内只存阶段报告相对路径（`<job>/<stage>/attempt-<n>.md`）。读取必须走 `ReportStore.read_stage_report` 的根目录校验；不要把绝对路径写进 `job_stages.report_path`。
- 同一阶段重复写入生成 `attempt-2.md`、`attempt-3.md`，永不覆盖旧文件。续跑、重试与测试清理都不要删旧 attempt；B3 对账依赖磁盘产物作为证据。
- 阶段报告截断按字节算 128 KiB，`full_length` 是原文字符数；截断后按 UTF-8 边界解码，不产生替换字符。不要改成按字符截断，契约单位是 KiB。
- B3 检测在 P1-07 只做到「文件存在 + 阶段仍 active + 无 done 事件 → 返回对账备注」。把任务改判 interrupted、把备注写进审计表并决定续跑起点是 P1-10 的事；不要在检测函数里改状态。
- `reconcile_note` 的 `seq` 必须是 NULL，只进 `JobDetail.reconcile_notes`，不进 SSE。P1-07 的 GF-13 已验证事件流仍为 1..8 无空洞。
- SM-03 现在是两层：12 个阶段文件与假图输出逐字相等（P1-07）；`reports` 行、`content_hash`、`report_id` 与 `report_ready` 由 P1-09 落库，GF-03 同时断言黄金哈希与终态事件顺序。
- 阶段报告 GET（1.10）只对 `done` / `failed` 且 `report_path` 非空时读文件；`pending` / `active` / `skipped` 返回 200 + `markdown: null`。路由只读：不触发对账、不改状态、不发事件。
- `current_stage` 取第一个 `active` 阶段，`queued` 与四个终态固定为 null。P1-08 的暂停只在阶段边界落地，落 `paused` 时没有 active 阶段，因此投影不需要为 `paused` 另加推断。
- 执行器上报的 `duration_ms` 是阶段虚拟耗时（假图每段 30 分钟），阶段事件的 `started_at` / `finished_at` 用服务端真实时钟。两者在假图下不相等是预期，不要用时间差覆盖执行器上报值。
- 执行器可注入 `Worker(executor=...)`，测试与后续持久化包装用它；生产走工厂默认值，不要在 Worker 里另建第二套选择逻辑。
- 后端不导入 `web`：GF-06 由测试把 `on_chunk` 接到 `web.progress.ProgressTracker`，产品代码只暴露 chunk 回调。
- 控制动作只有一个入口 `JobService.control`（`backend/app/services/job_service.py`），路由只做请求体校验与错误映射。`pause` / `resume` / `cancel` 的分支都在服务层用条件 UPDATE 重试，不要在路由或 Worker 里再写一份状态判断。
- 接受控制返回 202 `{job_id, accepted:true, action, accepted_at, expected_effect:"at_stage_boundary", status}`；重复请求返回 200 `{accepted:false, reason:"already_pending", status}`，只在 pause 对 `pause_requested`、cancel 对 `cancel_requested` 时成立；其余非法组合一律 409 `illegal_transition`，details 固定 `{from, action, rule}`（rule 可为 null）。`expected_effect` 三种动作都用 `at_stage_boundary`，这是冻结契约 1.6 的固定值，不要按动作另造字符串。
- 非法动作在 service 里追加一条 `transition_rejected` 审计（`broadcast=False`，seq 为 NULL）后再抛 409；路由只负责把 `JobControlError` 转成 `ApiError`。不要在路由层补审计，否则一次请求会写两条。
- `allowed_actions` 的唯一实现在 JobDetail serializer 的九状态表：queued `[cancel]`、running `[pause,cancel]`、pause_requested `[cancel]`、paused `[resume,cancel]`、cancel_requested `[]`、cancelled `[reanalyze]`、succeeded/failed `[retry,reanalyze]`、interrupted `[resume_from_checkpoint,retry,reanalyze]`。P1-09 加 retry 时改这张表，不要在路由另算。
- T09 与 T10 靠 `_worker_idle` 区分：读全局 `worker_lease` 行，要求 owner 未过期，且该 owner 名下没有 `running` / `pause_requested` / `cancel_requested` 任务；没有活租约视为空闲。测试里模拟「Worker 忙」必须先真拿一把租约并挂一个 running 任务，不要只改状态糊弄判断。
- 认领优先级固定为 control → resumed → queued。`claim_control_job`（cancel_requested 且无租约）与 `claim_resumed_job`（running 且无租约）只挂租约、不写状态事件；T09 的 `status_changed(running)` 在 resume 时已经写过，不要再补 queued→running。
- resume 前必须重算指纹：`graph_version` 相等且 `config_hash(config_snapshot, graph_version)` 等于库里的 `config_hash`，否则 409 `resume_fingerprint_mismatch`。`config_snapshot` 与 `config_hash` 仍然只读，恢复不得改写。
- pause 落地时清 `pending_action` 与任务租约，并写 `resume_from_stage=首个未完成阶段`；resume 使用该检查点起跑。不要用「阶段计数」或「当前时间」推续跑点。
- 恢复运行的累计统计从库中最新 stats 续接，`run_once` 终态写的是 `cumulative` 而不是 `result.stats`（后者只覆盖剩余阶段）。不要改回 `result.stats`，SM-07 的 13 条累计对账会立刻变红。
- 假图执行器从 `resume_from_stage` 索引开始，前缀阶段静默消费（不触发 `on_stage` / `on_chunk` / stats），已完成阶段行保持 `done`。未知阶段抛 `resume_stage_unknown`；不要改成重置阶段行或补发事件。
- 取消的终态写法分两类：queued 直接取消写一条零值 stats（seq 1）再写 `cancelled`（seq 2）；running / pause_requested / paused 在边界写累计 stats 再写 `cancelled`。P1-09 的 succeeded 只补一条终态前 stats，不要给 cancelled 再加第三条。
- 迟到判断在执行器返回后：状态仍是 `pause_requested` / `cancel_requested` 时置 succeeded，`status_changed.detail` 记 `pause_noop` / `cancel_noop`。P1-09 起这条路径也提交报告与 `report_ready`（SM-10 断言事件流末三条为 stats、status_changed、report_ready）。
- `Worker.run_once()` 返回 `WorkerOutcome(job, result, stopped)`，`stopped` 取 `cancelled` / `paused` / `lost` 或空；既有测试读 `outcome.job` / `outcome.result`，新增测试照此写，不要退回裸 `RunResult`。
- 控制动作的 `accepted_at` 用服务端时钟秒级，与任务时间戳同格式；不要用租约的毫秒格式。
- 终态写入只有一个入口：`JobService.finish_success` / `finish_failure`。两者都用条件 UPDATE（`WHERE id=? AND status IN (running, pause_requested, cancel_requested)`）判定赢家；rowcount=0 即输家，不写事件、不写报告。不要在 Worker 里先查状态再改，检查与写入必须是同一条 UPDATE。
- 成功事务的事件顺序固定：stats → status_changed(succeeded) → report_ready。`report_ready` 只在报告行同事务插入时追加，载荷 `{report_id, content_hash, rating, signal, url}`；不要先发事件后写报告，B5 靠这一条同事务消除。
- `report_document.finalize_report` 是报告字段的权威来源：job 元数据、`generated_at_source=job_clock`、`origin=new`、`schema_version=report-v1`、rating→signal 映射、data_quality_status / chart_snapshot_status 枚举兜底、`content_hash` 全部由服务端算；执行器 meta 里的同名字段会被覆盖，只有它提供的 `report_id` 会被保留。
- `content_hash` 只覆盖 `sections`：UTF-8、`ensure_ascii=False`、`sort_keys=True`、紧凑分隔符的 sha256。改字段或改分隔符都会改变黄金哈希，动之前先判断是不是契约变更。
- 失败终态把仍在 active 的阶段标 failed 并发 `stage_changed(failed)`；阶段后异常没有 active 阶段时，`status_changed.detail` 记 `post_stage_error`，不要凭空造一条失败阶段。
- 重试 `POST /api/v1/jobs/{job_id}/retry` 的幂等体哈希是 `sha256(canonical_json({job_id, mode}))`，与创建路径的 body_hash 不共享命名空间；同一把键先 replay 再看任务状态，和 1.3 的五步顺序一致。
- `same_config` 复制原 `config_snapshot` 并按当前 `graph_version` 重算 `config_hash`；`resume_from_checkpoint` 仅限 interrupted 且指纹一致，起点是第一个未完成阶段。原任务的任何列都不被重试修改。
- 重试出的新任务带 `retry_of_job_id` 溯源，不参与活动指纹，因此可与原任务并存；失败后再次重试会生成第三个任务，报告行的 `retry_of_job_id` 记录直接的溯源边。
- ID-09（PDF 缓存命中不重渲染）依赖 P3 的导出端点与渲染器，P1 不预埋。
- B5 的恢复分支（外部已置 succeeded 但缺 report_ready 或缺报告行）由 P1-10 对账处理；正常路径已在 P1-09 同事务消除，P1-10 不要再重写一遍正常终态。
- 启动对账只在 `Worker.acquire` 取得全局租约后、首次认领前跑一次；`TA_STARTUP_RECONCILE=0`（或 `Worker(reconcile_on_start=False)`）是回退开关。存在其他活跃租约时整套扫描跳过，不要在对账里再抢租约。
- 对账的存活判断只认全局 `worker_lease` 心跳（`LeaseService.live_owner`）。`job.lease_expires_at` 认领后不再续期，拿它当心跳会把健康长跑误判成崩溃；不要改回按任务租约过期扫描。
- `mark_interrupted` 只对 running / pause_requested / cancel_requested / paused 生效，用条件 UPDATE 与扫描值比较；扫描后状态已变则 rowcount=0，不改任何行。对账只写状态与一条 `status_changed(reason=reconcile)`，不跑图、不调模型。
- B3/B4 的 `detail` 取值存在契约内冲突：`crash-boundaries.md` B3/B4 写 `lease_expired` + 备注，`sse-events-v1.md` 第 8 节与假图参考实现用 `unregistered_stage_output` / `unregistered_report`。实现与可执行参考及 SSE 契约一致，备注照写；要统一措辞必须先走解冻流程。
- B3/B4 的 `reconcile_note` 与状态事件同事务提交，`seq` 为 NULL、不广播；检测顺序固定 `unregistered_report` > `unregistered_stage_output` > `lease_expired`，与假图 `FakeJobRunner.reconcile` 一致。
- 对账写入的 `resume_from_stage` 是 B3 感知的：active 阶段的报告文件已在盘上就跳过它，且保留原检查点作为下界（续跑任务的前缀阶段没有行，不能把起点提前）。retry 的 resume 模式优先取这个值，回落到阶段行推断；不要只按 `job_stages` 推，B3 会重复执行已产出阶段。
- 暂停检查点的定义是「`resume_from_stage` 非空，且所有 done/skipped 行的 `report_path` 仍可读」；任一条件不满足即 `interrupted(checkpoint_missing)`。不要只看目录是否存在。
- 成功提交前 Worker 会把执行器报告写到 `<job>/report.json`（临时文件 + `os.replace`，见 `ReportStore.write_final_report`）；写盘与提交之间崩溃即 B4。该文件只是证据：对账只记备注，绝不导入报告表、绝不把任务改成 succeeded；写文件失败只记日志，不影响任务成功（数据库提交才是权威）。

- 启动对账会把没有活租约的 cancel_requested 行（含 paused 上取消的 T20）判成 interrupted。产品里 Worker 常驻，取消请求落在 Worker 存活期间没问题；测试若要先发取消再起 Worker，必须先把 Worker 起起来（SM-14 已按此调整），否则取消会被当成孤儿。
- queued 行在对账中不动，随后正常认领（B1）；终态行一律不动（B6）。只有 succeeded 缺 `report_ready` 这一种状态会被追加事件，其余行不要做任何补写。

### 8.4 已经想清楚的实现口径

- 实时推送用短轮询数据库：Worker 可能在另一个进程，内存队列收不到；SQLite WAL 允许边写边读。
- 同步生成器交给 `StreamingResponse`，响应头按契约：`text/event-stream; charset=utf-8`、`Cache-Control: no-cache`、`X-Accel-Buffering: no`。
- 快照总是第一帧：`payload={job, last_seq}`，帧的 `id` 等于 `last_seq`，不写库。带游标时快照之后补发，和假图 `subscribe()` 一致。
- `stats` 限频交给写入侧保证（每阶段一条，真实阶段间隔远大于 2 秒）；流里不丢行。丢行会让交付序号出现空洞，和「补发连续」冲突。
- 任务已终态：发完快照（或补发）后立即关闭，不发心跳。
- 游标非整数或负数返回 400 `invalid_request`；低于窗口返回 410；高于当前最大序号也按 410 处理，这是契约空白，提交说明里记一笔。
- `Accept` 不含 `text/event-stream` 返回 400。TestClient 默认发 `*/*`，测试必须显式带头。
- FastAPI 自动生成的 405 是纯文本，不是契约错误体；在 `install_error_handlers` 里补一个 Starlette `HTTPException` 处理器，把它映射成 `method_not_allowed`。
