# R1 百度板块风控与负缓存（暖加载 p95 未达标）

一句话：先让 `sector_blocks` 能正常取到数据（`curl_cffi` 浏览器指纹已实测 200），再加 60 秒负缓存，保证风控即使再次出现也不会把每次暖请求变成一次上游重试。

## 二、本票口径（先定死，不在代码里临场改）

**D1 先修传输，再谈缓存。**

`sector_blocks` 单独走 `curl_cffi.requests.get(..., impersonate="chrome")`，超时仍为 10 秒。只有 `curl_cffi` 导入失败时才退回 `requests`；`curl_cffi` 的网络异常按现有 `classify_exception` 映射成四类数据源错误码，不新增错误码。

理由：负缓存只能把 3.8 秒降到毫秒，但板块数据仍然缺失；先恢复数据，再用负缓存兜住未来的风控。

**D2 负缓存只登记一个端点。**

新增负缓存表，只有 `stock:snapshot:sector_blocks` 登记 60 秒；其他端点未登记即 0 秒，行为与现在完全相同。不改 `STALE_AFTER` 的 24 小时正缓存 TTL —— 那是「成功数据多久算陈旧」，和「失败多久再试」是两件事。

**D3 负缓存不许挡住旧数据。**

优先级固定为：新鲜成功 > 旧成功转 `stale` > 负缓存里的失败。负缓存生效期间一律不调上游；只要还有成功的旧数据，就必须返回 `stale`，不能因为最近一次失败而把块降级成 `error`。这是 `market-data-envelope-v1` 的陈旧语义，不能推翻。

**D4 负缓存里存的是失败结果，不是空数据。**

命中负缓存时返回与首次失败相同的 `error_code`、`error_message`，`fetched_at` 保留首次失败时间，`from_cache=true`。不得返回 `status=empty`，也不得伪造新的抓取时间。

**D5 契约零变更。**

信封仍是四态加 `partial/failed_blocks`；错误码仍是四个；`api-v1`、`report-schema-v1`、SSE、任务状态机都不动。不新增接口、字段、配置项、环境变量。

**D6 不碰旧版。**

不改 `tradingagents/`、`web/`、`run_all.bat`、8501 入口。`tradingagents/dataflows/a_stock/signals.py` 里的同一风控只作为已知事实引用，不在本票修。

**D7 指标不达标就不算完成。**

`--live` 暖 p95 仍高于 1500 ms 时，票保持未完成，证据写清原因，不允许把 `--fixture` 的结果当成达标。

## 三、开工步骤

### 3.1 传输层（`backend/app/services/market_providers.py`）

1. 在 `_get`（第 574 行）旁新增 `_get_baidu(url, *, params, headers, timeout=10)`：
   - 顶部延迟导入 `from curl_cffi import requests as curl_requests`；
   - `curl_requests.get(url, params=params, headers=headers, timeout=timeout, impersonate="chrome")`；
   - `ImportError` 才退回现有 `requests.get`；其余异常按 `requests.Timeout` / `requests.RequestException` 的同类语义映射，`ProviderError("timeout")` 与 `as_provider_error` 保持原样；
   - 返回值只需满足 `.status_code` 与 `.json()`，把 `_check_status`、`_json` 的形参类型放宽到协议或 `Any`，避免类型检查被第三方 Response 卡住。
2. `DefaultMarketProviders.sector_blocks`（第 321 行）改调 `_get_baidu`。
3. 保留第 330-331 行的 `Result.code == 403` 检测：即使指纹过了，也可能返回风控体，仍然要映射成 `upstream_error` 与「百度接口风控拦截」。
4. 不改 `_UA` 常量：`impersonate` 已负责 TLS 与默认头，显式头保持现状，减少一次对比变量。

### 3.2 负缓存（`backend/app/services/market_cache.py`）

1. 增加 `NEGATIVE_TTL: dict[str, timedelta] = {"stock:snapshot:sector_blocks": MINUTE}`（常量 `MINUTE` 已存在，第 25 行）。
2. 增加 `_failures` 字典，键与 `_entries` 相同；存 `(failed_at, error_code, error_message, fetched_at_text)`。
3. `get_or_fetch`（第 116 行）判定顺序改成：
   - 负缓存未过期时，先看成功条目：新鲜就返回 `ok`；过期就地把旧数据包装成 `stale`（`stale_reason` 沿用 `ttl_exceeded` / `trading_day_mismatch`）。两种情况都不调 `fetcher`；
   - 负缓存未过期且没有成功条目 → 直接返回缓存的 `error`，不调 `fetcher`，不占 single-flight；
   - 负缓存已过期或未登记 → 走现有流程：新鲜成功返回缓存；否则 single-flight 调上游，失败时按第 163-177 行返回 `stale` 或 `error`，并写入新的负缓存。
4. 上游成功时删除该键的负缓存；上游失败时按 `NEGATIVE_TTL` 写入（未登记端点不写）。
5. `clear()`（第 194 行）同时清 `_failures`；`__len__` 口径保持只数成功条目。
6. 并发语义：负缓存命中必须立即返回，不能等待正在飞行的请求；否则一次 10 秒超时会把并发请求全部拖住。

### 3.3 不改的东西

- 不改 `stock_service.py` 的块顺序与 `partial` 拼装（第 52-73 行）。
- 不改 `p4_market_perf.py`；它的 `_measure_cold` 调 `cache.clear()`，会同时清掉负缓存，正好形成「冷样本真的打上游」的口径。
- 不加后台预热、不加定时重试、不改 24 小时正缓存。

## 六、回滚

- 单票一个本地提交；回滚即 `git revert <commit>`，无数据库迁移、无 schema 变更、无配置文件变更。
- 负缓存是进程内内存，重启即清空；回滚后旧行为立即可见。
- `curl_cffi` 已在依赖中，回滚不需要改依赖；如果传输层修复被证伪，可只保留负缓存作为止损，另开票继续查。

## 七、风险与坑

1. **百度可能再次升级风控**：指纹修复不保证长期有效。因此负缓存是必需项，不是可选项；两者要在同一票落地。
2. **403 有两种形态**：HTTP 403 与 HTTP 200 包体里的 `Result.code=403`。只处理一种会漏。
3. **负缓存最容易犯的错**是盖住旧数据。R1-T3 是硬门禁，不允许为了「暖 p95 好看」牺牲 `stale` 语义。
4. **single-flight 与负缓存的顺序**：负缓存命中必须在进入 flight 之前返回，否则并发请求仍会等满超时。
5. **冷样本会变慢**：指纹修复后 `sector_blocks` 真的会抓数据，冷 p95 可能从 865 ms 上升；4000 ms 是硬线，超了要查超时与重试，不是把线改宽。
6. **不要动 `tradingagents/`**：`signals.py` 有同样的 `requests` 风控注释，但旧版链路不在本票范围，改了会触发双栈回归。
7. **不要把探针写进测试**：本票测试全部打桩；`--live` 是人工步骤，不进 CI，不读 API Key。
8. **本机代理**：若日常开了系统代理，`curl_cffi` 与 `requests` 的代理读取规则不同；`--live` 结果 JSON 要记录是否走代理，避免把代理差异误判成代码效果。
