## 四、契约行为

依据：`contracts/api-v1.md` 第 177 至 226 行、`contracts/core-wireframes.md` W04、`contracts/interaction-checklist.md` A07 至 A10、`contracts/core-state-machine.md` 的 I01 至 I11。

### 4.1 控制动作（同一 jobId）

- `POST /api/v1/jobs/{jobId}/actions`，body `{"action":"pause"|"resume"|"cancel"}`。
- 已受理：202 `{job_id, accepted:true, action, accepted_at, expected_effect:"at_stage_boundary", status}`；重复提交同一动作：200 `{accepted:false, reason:"already_pending", status}`，两者都不算错误。
- 非法状态：409 `illegal_transition`，`details.from / action / rule` 指向 I01–I11；界面不自己判断合法状态，刷新详情并提示安全文案。
- 暂停只在阶段边界生效：202 后状态显示「暂停中」，并显示「已受理，将在当前阶段结束后生效」；收到 `status_changed = paused` 才显示「已暂停」。
- 继续用同一个 jobId；`resume` 202 后状态回 `running`，从下一阶段接着跑。
- 取消必须二次确认，文案固定「已产生的模型费用不退，且不会生成完整报告」；确认后显示「取消中」，终态 `cancelled` 后 `allowed_actions` 为空、没有报告入口。
- 任务刚好完成时取消会得到 409 `illegal_transition`：刷新详情为已完成并给报告入口，不弹通用错误。
- `allowed_actions` 只来自服务端；`status_changed` 不携带它，动作受理后要失效并重取详情，不复制状态表。

### 4.2 重试与续跑（创建新任务）

- `POST /api/v1/jobs/{jobId}/retry`，body `{"mode":"same_config"|"resume_from_checkpoint"}`，必须带 `Idempotency-Key`。
- `same_config`：新任务继承原参数，旧任务字段不变；201 跳新详情；200 + `X-Existing-Job` 表示已有相同任务，跳已有任务；`Idempotency-Replayed: 1` 按同一次意图处理。
- `resume_from_checkpoint`：新任务带 `resume_of_job_id` 溯源；界面说明从中断阶段继续、会补跑哪些阶段。
- 409 `resume_fingerprint_mismatch`：隐藏「从检查点继续」，只给「重新分析」；不提供强制绕过。
- 「重新分析」打开统一启动器（`/workbench?launch=1&ticker=<code>` 或工作台内），走全新幂等键；详情页不得直接 `POST /jobs`。
- 重复点击重试不得产生两个新任务：ref 守卫 + `disabled` 双重防连点，成功后跳转。

### 4.3 界面与错误

- 暂停/继续/取消成功与否都以服务端返回的 `status` 为准；受理后等 SSE 把状态推到目标值，必要时重取详情校准。
- 409 统一刷新详情；422 只显示 `ApiError.message`；网络错误保留当前界面并允许重试；429 显示等待秒数。
- 动作按钮的加载态只锁当前按钮或整组，不锁整页；确认框打开时不执行请求。
- 取消确认框复用 `Dialog` 的焦点陷阱与 Esc；焦点默认落在「不取消」或安全的次按钮上，关闭后焦点回「取消」按钮。

## 八、必须守的约束

- 动作按钮只按服务端 `allowed_actions` 渲染，不在前端推状态表；状态名只用九状态共享词汇。
- 暂停/取消 202 只表示受理，界面不得立刻写成「已暂停」「已取消」；等 SSE 或详情校准。
- 取消必须二次确认，文案固定；不确认不发任何请求。
- 重试与续跑必须带 `Idempotency-Key`；ref 守卫 + `disabled`，重复点击不产生第二个任务。
- `same_config` 与 `resume_from_checkpoint` 的结果都是新任务；旧任务不原地改参数、不改状态。
- `resume_fingerprint_mismatch` 不提供强制绕过，只给「重新分析」。
- 「重新分析」走启动器新幂等键，详情页不直接 `POST /jobs`。
- 409 刷新详情而不是弹通用错误；422/429/网络错误文案只来自 `ApiError.message` 或契约文案。
- 组件不直接 `fetch`，不写 `/api/v1` 字面量；只用 `api/jobs.ts` 的封装。
- 动作组不能破坏 P2-10 的 44px 与 390/360 布局；确认框在移动端全屏或可完整操作，不横向溢出。
- 一票一本地提交，不推送；存档单独提交。

## 九、容易踩的坑

1. `allowed_actions` 不在 `status_changed` 载荷里：动作受理后必须重取详情，否则按钮会停留在旧集合。
2. 202 的 `status` 可能是 `pause_requested` / `cancel_requested`，不是目标态；界面文案要沿用九状态映射，不自行改写。
3. `already_pending` 是 200 且 `accepted:false`，不是错误；不要当 409 处理，也不要重复发请求。
4. 暂停只在阶段边界生效；假图阶段可能瞬间结束，E2E 要用 `--stage-delay-ms` 放大窗口，并轮询 API 状态而不是固定等待。
5. 任务刚好完成时取消会 409；此时应刷新显示已完成与报告入口，而不是保留「取消中」。
6. 重试成功返回的是新 `JobDetail`，不是 `ControlResponse`；跳转与旧任务不变要分别断言。
7. 重试的幂等键属于一次点击意图；网络错误重试同一键，成功后换新键，避免第二次重试复用到旧任务。
8. `X-Existing-Job` 与 `Idempotency-Replayed` 都只从响应头判断，不看 job id 是否眼熟。
9. 续跑指纹不一致是 409 `resume_fingerprint_mismatch`；不要把它和 `illegal_transition` 混成一个分支。
10. 「重新分析」不是 `retry`；它进启动器并生成全新幂等键，不能复用旧任务的键。
11. 详情页已有 SSE，动作后不要把 `queryClient.setQueryData` 直接写成目标状态；让事件或详情 GET 决定。
12. 取消确认框关闭后要还原焦点；Dialog 已有焦点陷阱，但不要在请求中关闭或重复打开。
13. 390/360 下动作组可能换行，确认框 footer 要吸底可达，主/次按钮都要 44px。
14. 重试跳转用 `replace` 还是 `push` 要与启动器一致：成功进入新详情后返回不应回到旧任务的动作态。
15. 旧任务详情若仍开着 SSE，重试跳转前要正常卸载，避免旧连接在新页面里继续写缓存。
