## 四、输入与输出的事实

先读三个东西：`contracts/report-schema-v1.md`（§1 字段、§2 meta、§3 章节、§4 导入规则、§5 对照表）、`contracts/report-schema-v1.json`（机器可读）、`tests/fixtures/upgrade/legacy_report_v1.json`（输入样本）。

样本事实：

- 旧样本共 14 个键：`company_of_interest`、`trade_date`、7 个分析师键、`investment_debate_state`、`trader_investment_decision`、`risk_debate_state`、`investment_plan`、`final_trade_decision`。
- 它没有 `data_quality_summary`，所以转换结果不该有 `sec-quality`，`data_quality_status` 固定 `absent`。
- 它没有 `trader_investment_plan`，RC-01 的正向用例要自己复制一份样本加上该键，不要改黄金文件。
- `risk_debate_state.judge_decision` 与 `final_trade_decision` 文本完全相同（都是 1473 字符），可直接验证 judge 引用规则。
- 样本正文里没有 think 标签、代码围栏或 HTML 标签，清洗逻辑用这份样本测不出来。

两个容易踩的坑：

1. `final_state_v1.json` 不是这份旧样本的转换答案。它的 `origin` 是 `new`、`rating` 是 `Overweight`，而旧样本正文写的是 `Underweight`，它还多一个 `sec-quality`。它是新路径的黄金报告。断言「旧样本转出来等于 final_state_v1」会必错，转换结果要按契约 §1/§2/§4/§5 反推。
2. 黄金里 risk 的 judge 引用写成 `parts_ref: {"judge": "sec-decision"}`，不是在 `parts` 里放一个特殊字符串。schema 的章节对象允许字段就是 `id`、`title`、`body`（必填）与 `parts`、`parts_ref`、`legacy_aliases`（可选），没有第七个。

## 五、转换口径（照这个做）

1. 13 个章节 ID 与顺序按契约 §3 写成一份常量，测试从同一常量取，不要在测试里再抄一遍。
2. 七个分析师键按 §5 映射：`market_report`→`sec-market`，`sentiment_report`→`sec-sentiment`，`news_report`→`sec-news`，`fundamentals_report`→`sec-fundamentals`，`policy_report`→`sec-policy`，`hot_money_report`→`sec-hot-money`，`lockup_report`→`sec-lockup`。
3. `final_trade_decision`→`sec-decision`，`trader_investment_decision`→`sec-trader`，`investment_plan`→`sec-plan`，`data_quality_summary`→`sec-quality`（空或缺就整章不出现）。
4. 辩论：`investment_debate_state` 的五个子键进 `sec-debate.parts`，键名 `bull`、`bear`、`history`、`current`、`judge`；`risk_debate_state` 的 `aggressive_history`、`conservative_history`、`neutral_history`、`history` 进 `sec-risk.parts`，键名 `aggressive`、`conservative`、`neutral`、`history`。空子键直接丢弃。
5. risk 的 judge 与 `final_trade_decision` 文本完全相同时，写 `sec-risk.parts_ref = {"judge": "sec-decision"}`，不在 `parts` 里重复存文本；文本不同则照常进 `parts["judge"]`。
6. `trader_investment_plan` 只在非空且与 `investment_plan` 不同时保留，位置是 `sec-plan.legacy_aliases`，不参与 `body`。
7. `rating` 只认 `**Rating**: X` 精确解析，五档之外一律 `unknown`，不做关键词猜测。`signal` 由 `RATING_TO_SIGNAL` 映射。旧的 `extract_signal` 扫描值只进 `meta.signal_legacy`，渲染层不读它。
8. `price_target`、`stop_reference`、`time_horizon` 解析失败一律 null，不编造。
9. `generated_at` 固定 null，`generated_at_source` 固定 `unknown`，`origin` 固定 `legacy_import`，`job_id` 固定 null，`config_digest` 固定 null，`data_quality_status` 固定 `absent`，`chart_snapshot_status` 固定 `none`。禁止用文件 mtime 冒充生成时间。
10. `content_hash` 调用 `report_document.compute_content_hash(sections)`，参数与 P1-09 完全一致，不要另算一套。
11. `report_id` 由调用方注入，默认 `uuid4`。测试注入固定值，才能做「同输入同输出」的断言。
12. `ticker_name` 默认 null，不解析、不联网；显示层回退为代码，这是契约允许的。

两个实现选择，建议照此并在提交说明里记一句：

- 正文清洗只做 think 标签与裸代码围栏。跨章去重属于渲染层（现在在 `web/pdf_export.py` 的导出清洗里），不要在 DTO 层做：旧样本的 `debate.current_response` 与 `investment_plan` 文本相同，DTO 层去重会把章节内容删掉，还会让 `content_hash` 与「正文原样」冲突。
- 后端不能 import `web`（GF-06 的边界）。`signal_legacy` 的扫描顺序（`investment_plan` → `trader_investment_decision` → `final_trade_decision`，命中 BUY/SELL/HOLD，否则 `N/A`）要复制成模块内的私有小函数，注释写明与 `web/history.py::extract_signal` 对齐。
