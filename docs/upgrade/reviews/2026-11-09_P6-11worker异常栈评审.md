# P6-11 评审：worker 失败路径补异常栈

结论：通过。`backend/app/worker/main.py` 的异常分支补了 `exc_info=True`：失败分支 `logger.error` 紧跟原有 `finish_failure`，lease 丢失与已终态两个分支 `logger.warning` 后照旧返回。API 错误体、`error_message`、事件流、数据库与 `api-v1` 全部不变，栈只进服务端日志。新增 1 条测试直接断言日志里有 `Traceback` 与异常类名；全量 872 passed / 4 skipped。

基线 `2aa357e`（P6-10 收尾），本票两个本地提交，**未推送**。

## 一、为什么现在做

- P6-08 S6 首轮 `internal_error` 只留 code/message，控制台没有栈，二轮只能靠供应商 402 与响应体反推原因（P6-08 评审「偏离与坑」第 6 条、遗留第 2 条）。
- P6-09 在常驻入口跑通 DeepSeek 后，S6 的验收缺口只剩排障信息这一类；补栈不改任何对外行为，风险最低。
- 失败任务在 `jobs.db` 里本来就没有栈字段，事后无法补看；日志是唯一可留的证据位置。

## 二、改了什么

| 文件 | 改动 |
| --- | --- |
| `backend/app/worker/main.py` | 失败分支：`logger.error("analysis failed for job %s (code=%s): %s", ..., exc_info=True)`，随后照旧 `finish_failure`；lease 丢失、已终态两分支：`logger.warning(..., exc_info=True)` 后返回 |
| `tests/backend/test_terminal_retry.py` | 新增 `test_sm04_failure_logs_the_exception_traceback`：在 `caplog` 里断言 job id、`Traceback`、`_Boom`，同时断言 API 的 `error` 仍只有 `code`/`message` |

失败分支把原来的两次 `job_status` 查询合并为一次，判定语义不变：非 `running` / `pause_requested` / `cancel_requested` 即视为已终态，不再写失败。

未改：错误码映射、`error_message` 文案、`job_events` 写入、SSE 事件顺序、`api-v1` 响应形状、数据库 schema。
