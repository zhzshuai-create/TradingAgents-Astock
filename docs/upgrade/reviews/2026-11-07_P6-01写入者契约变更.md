# 2026-11-07 P6-01 写入者契约变更

结论：`api-v1.md` 新增可选字段 `write_mode`，`error-codes-v1.md` 新增错误码 `write_mode_legacy`（409）。两处都落在 `FREEZE-v1.md` 第 1 节的「允许变更，不升版本」范围内，契约仍为 v1。代码、测试、三份冻结文件与本次评审记录同一次本地提交。

## 一、改了什么

| 文件 | 改动 |
| --- | --- |
| `contracts/api-v1.md` | 1.8 的 `meta/options` 示例加 `"write_mode": "legacy"`；字段表加一行：可选 enum，`legacy` / `next`，缺省按 `legacy` 理解 |

## 二、为什么不需要升版本

`FREEZE-v1.md` 第 1 节允许两类不升版本的变更：

- **新增可选字段**：`write_mode` 是可选的，旧客户端完全不读它，行为与改动前一致；这正是字段表里写「缺省按 legacy 理解；旧客户端忽略后行为不变」的原因。
- **新增错误码**：`write_mode_legacy` 是新码，不复用 `active_conflict`、`idempotency_mismatch` 或 `illegal_transition` 的语义。旧客户端即使不认识它，也会照 `4xx + error.code + error.message` 的既有兜底路径显示文案。

没有改动任何既有字段的类型、必填性或含义，也没有改既有错误码的 HTTP 状态与用户动作，因此不触发升版本条件。

## 三、为什么五步判定顺序没变

创建路径的契约顺序仍是：

1. 幂等键命中 → 回放原任务；
2. 同键不同体 → 409 `idempotency_mismatch`；
3. 同配置活动任务 → 200 返回既有任务；
4. 不同配置活动任务 → 409 `active_conflict`；
5. 新建。

写入者开关只作为第 5 步的前置条件，插在 `job = Job(...)` 之前。前四步照旧回答，不产生写入：

- 客户端丢响应后用同一 `Idempotency-Key` 重放，仍拿到 200 与 `Idempotency-Replayed: 1`，不会被误判为失败；
- 已有同配置活动任务仍返回既有任务；
- 已有不同配置活动任务仍先报 `active_conflict`（WM-08 覆盖），不会把冲突错报成写入者问题。

`retry_job` 与 `create_job` 共用 `_create_once`，所以 `legacy` 下重试同样 409，不需要第二处判断。`pause` / `cancel` / `resume` 不创建任务，保持原行为。

## 四、META-01 断言调整

`meta/options` 原来是「恰好八个顶层键」的全等断言。新增 `write_mode` 后改为：

- 八个既有键必须都在（逐键断言保留，值不变）；
- 允许且仅允许多出 `write_mode` 一个顶层键，取值必须在 `legacy | next`。

理由是：契约把 `write_mode` 定为可选字段，响应端总会发送，客户端按可选解析。全等断言在「新增可选字段」时天然会挡路，属于新增字段的必然结果，不是放宽校验。`write_mode` 不进 `limits`、不进 `journal`，也不进 `ServerConfig.config_defaults()`，所以 `config_hash` 与幂等契约不受影响。

## 五、前端处理缺省的取舍

契约写「缺省按 legacy 理解」，前端却只在**显式** `write_mode === "legacy"` 时禁用提交。这是为了兼容尚未升级的旧后端：旧后端不返回该字段，新版前端不能把整个启动器锁死。一旦后端升级（本票之后），字段总会返回，显式判断就等价于契约语义。
