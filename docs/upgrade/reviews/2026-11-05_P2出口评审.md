## 3. A14 的唯一产品改动

### 3.1 改了什么

`frontend/src/features/jobs/JobListPage.tsx` 增加两段行为：

1. 滚动恢复：离开 `/jobs` 时把 `#main-content.scrollTop` 写入 `sessionStorage`，键为 `ta:jobs-scroll:<pathname><search>`；返回同一 URL 时恢复一次并立即删键。监听滚动记录最后位置，因为列表卸载先于 effect 清理，清理时 `scrollTop` 已被钳到 0。
2. 分页恢复：URL 带游标时从第一页重新拉到该游标（最多 20 页），全部页就绪后再恢复滚动。原实现把游标当 `initialPageParam`，冷启动或重新取数时只会得到最后一页。

### 3.2 为什么必须改

浏览器原生历史恢复作用于文档滚动，而本应用滚动的是 `#main-content`，列表又是 SPA 重渲染；实测后退回到列表顶部、且只加载 1 页。对照 `docs/upgrade/P2-13交接卡.md` 第七节口径，这两项属于 A14 的验收内容，不能靠等待浏览器实现。

筛选仍只存在 URL query，滚动位置不进 query、不进 `localStorage`；已加载页数由 URL 游标表达。

### 3.3 回退

- 只回退产品改动：`git checkout b19c089 -- frontend/src/features/jobs/JobListPage.tsx frontend/src/features/jobs/JobListPage.test.tsx`，列表回到「筛选与游标在 URL、滚动交给浏览器」，其余 P2 能力不受影响。
- 整票回退：删除 `e2e/e2e_p2.py`、`scripts/p05_ui_latency.py`、`docs/upgrade/reviews/2026-11-05_P2性能结果.json` 与本文件，再按上一行回退产品改动。后端、迁移头 `0005`、旧版 8501 入口始终不变。

## 4. P05-c 测量口径与结果

交付要求写的是「CDP `Network.dataReceived` 时间戳作为帧到达」。实测发现两条事实，必须改口径，否则数字不可用：

- 详情页用 `fetch` + `ReadableStream` 读事件流（`api/sse.ts` 的 `response.body.getReader()`），不是 `EventSource` API，因此 CDP 的 `Network.eventSourceMessageReceived` 从不触发。
- `Network.dataReceived` 只报 TCP 块，一次可能带多帧，无法把块归因到具体阶段；早先用它配对得到 1505 ms、4542 ms 两个伪样本，都不是界面延迟。

最终测量改为页面内埋点，同一次运行同一时钟：

- 到达：初始化脚本包装 `/events` 的 `fetch` 与 `reader.read()`，每次 `read()` 解析出 `stage_changed` 时记 `performance.now()`，并取 `payload.stage_id`；
- 可见：`MutationObserver` 记录同一 `stage-<id>` 第一次文案变化的 `performance.now()`；
- 配对：同一 `stage_id` 的帧到达后，该阶段按钮的第一次文案变化；快照回放中已经渲染完、没有新变化的帧不产生样本。

结果（`docs/upgrade/reviews/2026-11-05_P2性能结果.json`）：

| 项 | 值 |
| --- | --- |
| 样本数 | 25（3 个任务，每个 18.7 秒左右） |
| P05-c 中位 | 9.3 ms |
| P05-c P95 | 12.1 ms |
| P05-c 最小/最大 | 4.1 / 12.4 ms |
| P05-a 中位 | 4 ms（引用 `2026-11-05_P1-13性能结果.json`，未重测） |
| P05-b 中位 | 1.984%（引用同一文件，上限 5%） |
| P05 合计 | 13.3 ms，硬线 500 ms，通过 |

口径差异写在这里，不把 P05-c 说成端到端网络时延：它从应用代码拿到帧开始，到 DOM 文案变化为止，不含服务端到浏览器之间的网络与内核缓冲；那一段由 P05-a 覆盖。两端相加是本阶段可复现的合计值。
