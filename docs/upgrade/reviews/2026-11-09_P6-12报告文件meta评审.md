# P6-12 评审：report.json 内嵌 meta 与落库行对齐

结论：通过。worker 现在先把执行器报告 finalize 成 `finish_success` 将要落库的同一份 payload，再写 `<job>/report.json`，然后把同一 payload 与同一 `generated_at` 交给终态事务。写盘仍在提交之前，B4 语义不变；文件里的 `job_id`、`origin`、`generated_at`、`config_digest`、`chart_snapshot_status`、`data_quality_status`、`content_hash` 与报告行逐项相等。全量 873 passed / 4 skipped。

## 一、问题是什么

P6-09 真实任务 `6873fe1d` 的 `report.json` 内嵌 meta 是：

```text
job_id=null  origin=legacy_import  generated_at=null
config_digest=null  chart_snapshot_status=none  data_quality_status=absent
```

同一任务的数据库行与 API 都是 `origin=new`、`job_id` 已填、`generated_at`/`config_digest` 齐全、`chart_snapshot_status=frozen`。原因是顺序：

1. 执行器返回 `build_legacy_report(last_chunk)`，meta 是 legacy 形状的默认值；
2. worker 把这团原始报告直接写进 `report.json`；
3. `finish_success` 在事务里才调 `finalize_report` 生成权威 payload 落库。

文件因此永远停留在第 1 步的默认值。它不影响 API 与数据库，但 B4 证据（崩溃后人工查看的报告文件）会给出错误的来源、时间和快照状态。

## 二、改了什么

| 文件 | 改动 |
| --- | --- |
| `backend/app/services/job_service.py` | 新增 `build_success_report()`：读取 job 行，用给定 `generated_at` 生成与终态事务同源的 payload；`finish_success` 增加可选 `generated_at`；两条路径共用 `_finalize_success_payload()`（含 chart 状态覆盖与 `finalize_report` 调用） |
| `backend/app/worker/main.py` | 成功与 `pause_noop`/`cancel_noop` 两个终态分支：捕获一次 `generated_at` → `build_success_report()` → 写 `report.json` → `finish_success(report=同一 payload, generated_at=同一值)`；新增 `_prepare_report()` 收敛这段 |
| `tests/backend/test_terminal_retry.py` | 新增 `test_sm03_report_artifact_matches_the_committed_row`，逐项比对文件 meta 与报告行 |
| `tests/backend/test_chart_snapshot.py` | RPT-T1 增补：frozen 时文件 meta 的 `chart_snapshot_status` 与 `config_digest` 同 row 一致 |

未改：`finalize_report` 本身、报告表 schema、`api-v1` 响应、SSE 事件顺序、`chart_snapshot.json` 格式、错误码、对账逻辑。

## 三、为什么不是「提交后再写文件」

`report.json` 的契约角色是**提交前**的证据：写完文件、提交前崩溃 → 对账看到完整报告，记 `unregistered_report`，绝不自动导入（B4）。改成提交后写会把这段窗口变成「已 succeeded、但没有文件」，属于改崩溃边界语义，不是修 meta。因此保留原顺序，只把写入内容换成最终 payload。
