# P6-15 评审：P05 性能用例在 CI 上偶发红

结论：CI 的 `windows-latest, 3.13` 腿在一次文档提交里偶发红，判定为共享 runner 的固定写库开销噪声，不是产品性能回归。按方案 A 只把压测阶段从 500ms 提到 2000ms，预算、样本数与断言不动。修复提交 `e445401` 的 [run 42597719440](https://github.com/zhzshuai-create/TradingAgents-Astock/actions/runs/42597719440) 与随后文档提交 `04cf394` 的 [run 42601972943](https://github.com/zhzshuai-create/TradingAgents-Astock/actions/runs/42601972943) 结论均为 `success`，两次都是四条测试腿全绿；本地单用例连跑 3 次、整文件与干净克隆均通过。

## 一、现象

失败只有一条：`test_p05_server_latency_and_stage_gap_stay_within_budget`，run `42594570849` 的 `windows-latest, 3.13` 腿，注解原文 `assert 12.148973774628221 <= 5.0`（对应第 387 行，间隙偏差中位数超过 5% 预算）。

同一次 run 的 `ubuntu-latest, 3.13` 腿通过；上一代码头 `8da2a23` 的 run `42591732202` 同用例通过；本地 500ms 口径下延迟中位数 4.3ms（预算 500ms）、间隙偏差中位数 2.42%（11 个样本 1.11–3.19%）。

## 二、根因

间隙是前一阶段 `done` 写库、stats 事件与下一阶段 `started` 写库的固定开销，和阶段时长无关：本地约 8–17ms，共享 runner 上约 60ms。500ms 阶段下 60ms 就是约 12%，超过 5%。阶段越短，这个固定开销占比越大，所以同一个用例在慢 runner 上偶发红，而产品行为没有变化。

## 三、修法

`tests/backend/test_kernel_perf_faults.py:375`：

```text
- measurement = p05_latency.measure()
+ measurement = p05_latency.measure(per_stage_ms=2000)
```

未改：`p05_latency.measure()` 与 `--per-stage-ms` 的默认值（保持 500ms，已归档性能证据口径不变）、`LATENCY_BUDGET_MS = 500.0`、`STAGE_GAP_BUDGET_PERCENT = 5.0`、延迟 5 个样本与间隙 11 个样本、全部断言、产品代码。

选 2000ms 的理由：固定约 60ms 开销在 2000ms 下约 3%，距 5% 预算留约 2 个百分点；测的仍是 `done` 到下一个 `started` 的写入延迟占阶段时长的比例，且更接近真实阶段时长。代价是用例从约 6s 变约 25s，CI 每条测试腿多约 18s。
