核心语义词典

版本：v1（2026-10-29 冻结）

目的：让每个用户操作只对应一个服务端语义。前后端、文档、测试一律使用本表的词与文案，不再用页面文案猜状态。

旧版现状依据：web/progress.py（ProgressTracker 的四个布尔位 is_running / is_complete / is_paused / stop_requested 加 error 字段）、web/jobs.py（进程内 _jobs 字典）、web/runner.py（守护线程执行）。旧版没有持久化状态，进程重启即丢失全部任务。

1. 十二个核心词

新建分析

  • 用户看到：首页输入代码与日期，点「开始分析」，进入任务页，看到排队或执行中的阶段进度。
  • 服务端做：创建一条 job 记录，状态 queued；Worker 认领后转 running。
  • 是否可能产生模型费用：会。执行开始后每个阶段都会调用模型。
  • 旧版现状：创建 tracker 的同时立刻起守护线程，没有排队态；同参数重复点击靠前端禁用按钮兜底。

重新分析

  • 用户看到：在报告页或任务页点「重新分析」，得到一个全新任务，旧报告仍在历史里。
  • 服务端做：以当前界面配置新建一条 job，retry_of_job_id 为空；旧 job 保持原终态不变。
  • 是否可能产生模型费用：会，全额。
  • 旧版现状：2026-10-27 之后已是新 job id 语义，与本表一致。

重试

  • 用户看到：失败页或中断页点「使用相同参数重试」，得到一个标注「重试自 #旧编号」的新任务。
  • 服务端做：读取旧 job 保存的配置深拷贝，新建 job 并写 retry_of_job_id = 旧 job id；旧 job 不动。
  • 是否可能产生模型费用：会，全额（旧版没有检查点，重试等于重跑）。
  • 与「续跑」的区别：重试不复用任何阶段产物；续跑复用。两者不得混用同一个按钮文案。
  • 旧版现状：2026-10-27 已实现同参数重试（新 job id），但配置深拷贝只存在内存里，进程重启后无法重试。

从检查点继续（续跑）

  • 用户看到：中断页点「从检查点继续」，弹出确认框，列出将复用哪些已完成阶段、将从哪个阶段开始、预计还会调用哪些模型；确认后才开始。
  • 服务端做：校验配置指纹与图版本与中断时一致；新建一条 job，带 resume_of_job_id 与起始阶段；已完成阶段的报告从旧 job 复制，不重新调用模型。
  • 是否可能产生模型费用：会，但只发生在未完成阶段。
  • 前置条件：配置指纹或图版本不匹配时，本操作不可用，界面只给「重新分析」。
  • 旧版现状：不存在。进程重启后任务消失，没有检查点可续。

暂停中（pause_requested）

  • 用户看到：点「暂停」后按钮变为不可再次点击，进度条旁显示「暂停请求已提交，将在当前步骤结束后生效」。
  • 服务端做：写入暂停请求；当前正在流式输出的步骤跑完，执行停在步骤边界，状态转 paused。
  • 是否可能产生模型费用：当前步骤内已发生的调用不会退回；不会新增步骤调用。
  • 为什么要有请求态：暂停只能落在步骤边界，不能打断一次模型调用；没有请求态时，「点了暂停但还在跑」会被用户理解成按钮坏了。
  • 旧版现状：pause() 立即置 is_paused 并清 gate，界面上没有「请求已提交」的中间态。

已暂停（paused）

  • 用户看到：进度停在某个阶段，显示「已暂停」与「继续」「取消」两个按钮；已完成阶段的报告仍可查看。
  • 服务端做：执行停在步骤边界，检查点（已完成阶段报告 + 配置快照）落盘；Worker 租约释放，可以接别的任务。
  • 是否可能产生模型费用：不会新增。
  • 旧版现状：is_paused gate 生效，但任务仍占着那个守护线程；进程重启后暂停态丢失。

取消中（cancel_requested）

  • 用户看到：点「取消」后显示「取消中，正在收尾当前步骤」，按钮不可重复点击。
  • 服务端做：写入取消请求；当前步骤收尾后不再推进新步骤，状态转 cancelled。若收尾期间图恰好完成，则以 succeeded 结束并提示「任务在取消请求到达前已完成」。
  • 是否可能产生模型费用：当前步骤内已发生的不会退回；不会新增步骤调用。
  • 旧版现状：request_stop() 立即清空全部阶段报告与统计，没有收尾态，用户点完取消看到的是进度瞬间归零。

已取消（cancelled）

  • 用户看到：任务页显示「已取消」，已完成阶段的报告以只读形式保留，可展开查看；没有「自动重新开始」之类的动作。
  • 服务端做：终态。不自动重排、不自动重试。
  • 是否可能产生模型费用：不会。
  • 旧版现状：停止后 tracker 被清空，历史里看不到这次任务存在过。

连接中断

  • 用户看到：任务页顶部出现「连接已断开，正在重连」；重连成功后进度从断点继续显示，不丢失已渲染内容。
  • 服务端做：只影响浏览器与 SSE 通道；job 状态完全不变。重连带 Last-Event-ID，服务端从该序号之后续传事件。
  • 是否可能产生模型费用：不会。
  • 旧版现状：刷新页面会重跑整个 Streamlit 脚本；同进程内任务还在，但换浏览器或换设备看不到任务。

执行中断（interrupted）

  • 用户看到：任务页显示「执行中断」，说明原因（服务重启 / Worker 租约失效），给出「从检查点继续」和「重新分析」两个显式选项，没有任何自动动作。
  • 服务端做：终态。服务启动时对账：租约过期且状态不是终态的 job 一律改判 interrupted，不自动重放。
  • 是否可能产生模型费用：不会自动产生。只有用户显式确认续跑或重分析才会。
  • 为什么不用 failed：failed 表示「执行过并且报错」，interrupted 表示「不知道执行到哪了」。两者的处理动作不同，混用会让对账失去意义。
  • 旧版现状：进程重启后任务直接从 registry 消失，用户看到「任务不存在」。

已完成（succeeded）

  • 用户看到：任务页显示「已完成」与最终信号、统计（模型调用次数、token 数、耗时），可进入报告页；报告页只读。
  • 服务端做：终态。报告以不可变 report_id 提交；网页、Markdown、PDF 由同一份结构生成；PDF 需显式导出请求。
  • 是否可能产生模型费用：不会。查看报告零副作用。
  • 旧版现状：is_complete 为真；PDF 在渲染报告时重新拉行情，有副作用。

已失败（failed）

  • 用户看到：任务页显示「已失败」与错误摘要，已完成阶段的报告只读保留，给出「使用相同参数重试」和「重新分析」。
  • 服务端做：终态。记录错误码与错误文本；不覆盖原任务。
  • 是否可能产生模型费用：不会新增。
  • 旧版现状：error 字段存字符串，阶段报告在部分路径下被清空。

3. 禁用词

以下说法在界面与文档中禁用，因为它们在旧版里各自指代过不止一件事：

  • 「停止」：旧版既表示取消又表示清空进度。一律改用「取消」。
  • 「重跑」：不区分重试与续跑。按语义分别写「使用相同参数重试」「从检查点继续」。
  • 「任务丢了」「任务不存在」：进程重启后的任务一律是 interrupted，界面必须给出原因与两个显式选项。

1. 状态属性表

「占用 Worker」指是否持有执行租约。Worker 全系统只有一个，串行执行。

两个刻意的设计决定：

  • paused 不占 Worker。暂停可能持续很久，占着唯一 Worker 会堵死整条队列。代价是恢复时要重新抢租约。
  • interrupted 不给「恢复」，只给「续跑 / 重分析」，且两者都创建新 job。原 job 保持终态，对账时能清楚看到「哪一次执行断了、断在哪」。

4. 对账规则（服务启动时）

启动时扫一遍 job 表，逐条按下面顺序判定：

  1. 状态是终态：不动。
  2. 状态是 queued：不动，等 Worker 认领。
  3. 状态是 paused：检查点文件存在则不动；不存在则改判 interrupted，原因记 checkpoint_missing。
  4. 状态是 running / pause_requested / cancel_requested：租约心跳超过阈值即改判 interrupted，原因记 lease_expired。

对账只改状态和写一条 status_changed 事件，不触发任何执行，不调用任何模型。

幂等与冲突决策表

版本：v1（2026-10-29 冻结）

目标：同一个意图重复提交，永远只产生一个会花钱的执行。

三个键的定义：

  • 幂等键 Idempotency-Key：客户端生成的 UUID，随创建请求提交，服务端按它去重。
  • 活动配置指纹：ticker + trade_date + config_hash。config_hash 是模型配置、阶段开关、图版本的规范化哈希。
  • 活动任务：状态属于 queued / running / pause_requested / paused / cancel_requested 的任务。

1. 创建请求的判定顺序

创建接口按下面顺序判定，命中即返回，不再往下走：

步 条件 响应 说明
1 幂等键已存在且请求体哈希相同 200 + 原 job 重复提交，返回原任务
2 幂等键已存在但请求体哈希不同 409 idempotency_mismatch 同一个键提交了两种意图，属客户端 bug，必须报错而不是猜
3 幂等键未命中（未携带或首次出现），但存在同活动配置指纹的活动任务 200 + 该 job，响应头 X-Existing-Job: <id> 用户连点「开始分析」的典型场景
4 同 ticker + 同 trade_date，配置不同，且存在活动任务 409 active_conflict，body 带现有 job id 让用户自己决定：等它跑完，还是先取消
5 以上都不命中 201 + 新 job 正常创建

第 3 步与第 4 步的区别：配置完全相同就是同一个意图，直接复用；配置不同是另一个意图，不能替用户做主。

第 3 步必须覆盖「首次出现的新键」这种情况。若只认「未携带键」，二十个各带不同键的相同请求会全部落到第 5 步，与第 4 节的并发裁决矛盾。Day 6 的假账本按这个口径实现，见 tests/fake_analysis_graph.py::FakeJobLedger.create。

3. 不自动重放清单

以下场景服务端永不自动创建新执行，只能由用户显式触发：

4. 并发创建的裁决

二十个并发创建请求带同一个活动配置指纹时，最终必须恰好一个 job 处于活动状态，其余十九个拿到 200 + 同一个 job id。实现上靠数据库唯一约束（uniq_active_fingerprint 部分唯一索引：仅对活动状态生效）兜底，不靠应用层先查后插。

进程重启 任务消失 interrupted + 人工选项

崩溃边界预期表

版本：v1（2026-10-29 冻结）

这里不承诺绝对无损。原则只有一条：无法确认执行位置时，结果是 interrupted 加人工对账，不是自动重跑。 自动重跑意味着可能重复付费，且用户不知道哪一份结果是权威的。

六个时点按执行顺序排列。每个时点给出：崩溃前已落盘的东西、重启后可观测的证据、期望状态、是否可能重复付费、处理动作。

B1 任务已创建，Worker 尚未开始

  • 已落盘：job 行（queued）、配置快照、幂等键记录。无租约。
  • 重启后证据：job 表里有 queued 行，审计表只有一条 created 记录（审计记录不属于 SSE 六类事件，不占 SSE 序号）。
  • 期望状态：仍 queued。Worker 启动后正常认领。
  • 是否可能重复付费：否。一次模型调用都没发生。
  • 处理动作：无。这是唯一不需要人工介入的崩溃时点。

B2 图已开始，尚无阶段报告

  • 已落盘：job 行（running）、租约心跳、stage_changed 事件若干。无阶段报告文件。
  • 重启后证据：租约心跳停在崩溃时刻；事件表最后一条是某个 stage_changed；报告目录里没有该 job 的阶段产物。
  • 期望状态：对账改判 interrupted，原因 lease_expired。
  • 是否可能重复付费：崩溃前已发生的调用无法收回，但不会自动再花一次。
  • 处理动作：界面给「从检查点继续」（此时等于从头跑，但走续跑通道、有确认框）与「重新分析」。

B3 阶段已完成，事件尚未保存

  • 已落盘：某阶段的报告文件已写盘；stage_changed(done) 事件还没写进事件表。
  • 重启后证据：报告目录里有阶段产物，但事件表里该阶段仍是 active。
  • 期望状态：interrupted，原因 lease_expired；对账额外写一条 reconcile_note 审计记录（不占 SSE 序号、不广播），内容「发现未登记的阶段产物：<阶段名>」，同时出现在 JobDetail.reconcile_notes。
  • 是否可能重复付费：续跑时该阶段被识别为已完成，不重复调用。
  • 处理动作：人工对账。续跑起点取「事件表里最后一个 done 的下一阶段」与「磁盘产物里最后一个完整阶段」的较后者的下一阶段，保证不漏不重。

B4 核心报告已落盘，应用数据库尚未提交

  • 已落盘：最终报告文件在磁盘；job 行仍是 running。
  • 重启后证据：报告文件存在且内容完整；job 表没有 succeeded。
  • 期望状态：interrupted，原因 lease_expired。不自动改判 succeeded——数据库没提交就是没提交，替它补状态等于伪造执行历史。备注「发现一份未登记的完整报告」写入 JobDetail.reconcile_notes，不占 SSE 序号。
  • 是否可能重复付费：续跑或重分析才会花；对账本身不花。
  • 处理动作：界面提示「发现一份未登记的完整报告」，给三个选项：导入为报告（origin=manual，与任务解耦）、从检查点继续、重新分析。导入动作只写报告表，不改 job 状态。

B5 报告已提交，完成事件尚未发送

  • 已落盘：job 行 succeeded、报告行、内容哈希。SSE 客户端还没收到 report_ready。
  • 重启后证据：job 表是 succeeded；事件表缺 report_ready。
  • 期望状态：保持 succeeded。对账补发一条 report_ready 事件（序号续接），让重连的客户端能拿到。
  • 是否可能重复付费：否。
  • 处理动作：无。补事件不算重放，它只是把已经发生的事实广播出去。

B6 用户请求取消时，图正在完成收尾

  • 已落盘：cancel_requested 已写；图在最后一步收尾。
  • 两种结局都合法，取先落盘者：
  • 取消先确认：cancelled，收尾产物丢弃，界面说明「任务已取消，最后一步的结果未保留」。
  • 完成先提交：succeeded，取消记为 no-op，界面说明「任务在取消请求到达前已完成」。
  • 重启后证据：看 job 表终态与事件表里 status_changed 的先后序号即可还原当时谁先落盘。
  • 期望状态：二者之一，不允许出现半状态（既不是 cancelled 也不是 succeeded）。
  • 是否可能重复付费：否。
  • 处理动作：无。实现上靠「收尾提交与取消确认共用同一把任务级锁」保证互斥。

汇总

时点 期望状态 自动动作 人工动作
B1 queued Worker 认领 无
B2 interrupted 无 续跑或重分析
B3 interrupted + reconcile_note 无 对账后续跑或重分析
B4 interrupted 无 导入报告 / 续跑 / 重分析
B5 succeeded 补发 report_ready 无
B6 cancelled 或 succeeded 无 无

六个时点里只有 B1 和 B5 不需要人。其余四个一律停住等人，这是刻意的：停住的代价是用户多点一次按钮，自动重跑的代价是可能多花一次钱并且说不清哪份结果算数。

3. 章节结构（ReportDTO.sections）

  • sections 为对象，键为稳定章节 ID；顺序由下表固定，前端按表渲染目录，禁止依赖数组下标。

4. 版本与导出规则

  1. 每次成功分析生成新 report_id；重跑、重试一律新建，不覆盖旧报告。
  2. 同 ticker_code + analysis_date 允许多版本共存；列表按 generated_at 倒序，generated_at 为 null 的排最后。

接口契约 v1：任务、报告与市场数据

版本：v1（2026-10-29 冻结）

日期：2026-10-29 状态：冻结候选（Day 4 交付） 配套文件：market-data-envelope-v1.json（数据信封 Schema）、sse-events-v1.md（事件流）、error-codes-v1.md（错误字典）、job-state-machine.md、idempotency-conflicts.md、report-schema-v1.md

目标：前端只依赖本契约就能画完所有页面，不读 LangGraph 原始对象、不解析 markdown 猜状态、不自己决定按钮能不能点。

0. 通则

项 规定
前缀 所有接口在 /api/v1 下，版本号进路径
编码 请求与响应均为 application/json; charset=utf-8，Markdown 与 PDF 接口除外
字段命名 snake_case，沿用 report-schema-v1，不做 camelCase 转换
时间 时间点用 ISO8601 带时区，如 2026-10-29T09:31:05+08:00；日期用 YYYY-MM-DD
请求 ID 每个响应带 X-Request-Id；客户端可自带，服务端生成时优先用自带的
未知字段 响应新增字段客户端必须忽略；请求含白名单外字段一律 422，不静默丢弃
分页 limit 默认 20、最大 100；cursor 为不透明字符串；响应 {items, next_cursor}，next_cursor 为 null 表示到底
金额与百分比 价格单位元；change_pct 为百分数原值（2.35 表示 +2.35%）；amount_wan 单位万元；资金流各项单位元
鉴权 P0 为本机单用户，不做鉴权；契约保留 unauthorized 错误码，未来加鉴权不改路径
未实现接口 P0 只冻结市场接口结构、不实现；调用返回 501 not_implemented，不用 404 冒充

数据类接口（第 3 章）统一使用 market-data-envelope-v1 信封；任务与报告接口不使用信封，直接用错误体。

数据源失败与接口失败的分工：

  • 数据源取不到数据：HTTP 200，信封 status = error 或该区块 error，error_code 用 upstream_timeout 等数据源码。
  • 请求本身不合法、对象不存在、状态冲突：HTTP 4xx/5xx，错误体见 error-codes-v1.md。

前端据此区分「接口坏了」与「这只票今天没数据」，两种情况显示不同文案。

1.3 创建任务

POST /api/v1/jobs
Idempotency-Key: <uuid>        （必需）

请求体：

{
  "ticker": "000629",
  "analysis_date": "2026-10-29",
  "config": {
    "llm_profile": "deepseek-default",
    "parallel_analysts": true,
    "stage_toggles": {"policy": true, "hot_money": true, "lockup": true}
  }
}
字段 必需 说明
ticker 是 6 位代码或中文名；服务端按 resolve_ticker 归一化后回填 ticker_code。中文名模糊匹配到多只时报 422 ticker_ambiguous，details.candidates 最多 5 个
analysis_date 是 不接受未来日期，报 422 invalid_date
config 是 只允许白名单键：llm_profile、parallel_analysts、stage_toggles。多一个键报 422 config_unknown_key
config.llm_profile 是 服务端预置配置的 id，如 deepseek-default；非法值报 422 config_invalid_value 并返回允许值
config.parallel_analysts 否 缺省取服务端默认值
config.stage_toggles 否 缺省全部开启；关掉的阶段在 stages 里显示 skipped

客户端不能提交 backend_url、api_key、模型名以外的服务端配置——这三类一律按 config_unknown_key 拒绝。

响应按 idempotency-conflicts.md 第 1 节的五步判定：

情况 状态码 说明
新建成功 201 返回 JobDetail，status = queued
同键同体重放 200 返回原 job，Idempotency-Replayed: 1 响应头
同键不同体 409 idempotency_mismatch
无键但同活动指纹 200 返回该 job，响应头 X-Existing-Job: <job_id>
同票同日不同配置且已有活动任务 409 active_conflict details.active_job_id 给出当前活动任务，由用户决定等待或取消
没带 Idempotency-Key 400 idempotency_key_required

Idempotency-Key 作用域为创建接口，保留 24 小时；24 小时内重放返回当时的响应体与状态码。

1.4 任务列表

GET /api/v1/jobs?status=running,failed&ticker=000629&date_from=2026-09-01&date_to=2026-10-29&active=true&limit=20&cursor=...
  • status 可逗号分隔多值；ticker 精确匹配代码。
  • date_from / date_to 按 analysis_date 闭区间过滤；格式错误或晚于今天报 422 invalid_date。
  • active=true 只返回非终态任务（queued、running、pause_requested、paused、cancel_requested），供活动任务条使用。它与 status 互斥，同时出现报 400 invalid_request，details.field = "active"。
  • 排序固定 created_at 倒序；同秒内按 job_id 升序，保证分页稳定。
  • 返回 {items: JobSummary[], next_cursor}。
  • 该接口零副作用，不改变任何 job 状态。

  • 返回 JobDetail。
  • jobId 不存在返回 404 job_not_found；不自动创建任务（旧版 get_or_create_job 的行为在本契约中废止）。

1.6 控制接口：受理不等于生效

POST /api/v1/jobs/{jobId}/actions

请求体：

{"action": "pause"}

action 枚举：pause | resume | cancel。

语义：这三个动作都是异步请求。服务端只写请求标记，真正生效落在阶段边界（暂停、取消）或 Worker 空闲时（继续）。

结果 状态码 响应
已受理 202 {job_id, accepted: true, action, accepted_at, expected_effect: "at_stage_boundary", status}
重复提交同一动作 200 {job_id, accepted: false, reason: "already_pending", status}，不写第二条请求
状态不允许该动作 409 illegal_transition details.from / details.action / details.rule 指向非法转换编号（I01–I11）

按钮可用性完全由 allowed_actions 决定：

状态 allowed_actions
queued cancel
running pause, cancel
pause_requested cancel
paused resume, cancel
cancel_requested 空数组
cancelled reanalyze
succeeded retry, reanalyze
failed retry, reanalyze
interrupted resume_from_checkpoint, retry, reanalyze

六个动作对应的真实调用：

allowed_actions 项 调用
pause / resume / cancel POST /jobs/{id}/actions
retry POST /jobs/{id}/retry，mode = same_config
resume_from_checkpoint POST /jobs/{id}/retry，mode = resume_from_checkpoint
reanalyze POST /jobs，用当前界面配置，全新幂等键

1.7 重试与续跑：创建新任务

POST /api/v1/jobs/{jobId}/retry
Idempotency-Key: <uuid>        （必需）

请求体：

{"mode": "same_config"}
mode 适用状态 新 job 字段 原 job
same_config failed, interrupted, succeeded retry_of_job_id = 原 id，配置取原 job 深拷贝 保持原终态
resume_from_checkpoint interrupted resume_of_job_id = 原 id，resume_from_stage = 首个未完成阶段 保持 interrupted

paused 的「继续」不走本接口，走 1.6 的 resume 动作：同一个 job、同一个 id，这是暂停与中断的关键区别。暂停状态下检查点缺失时，对账已把它改判 interrupted，届时才用 resume_from_checkpoint。

  • 该接口会产生新的模型费用，因此必须带 Idempotency-Key，判定顺序与 1.3 相同。
  • 报告页的「重新分析」不另设接口：report.job_id 非空时调用本接口 mode = same_config，配置来源即原任务；历史导入报告 job_id 为 null，改为打开启动器并预填股票与分析日期。
  • resume_from_checkpoint 时 config_digest 或 graph_version 不匹配，返回 409 resume_fingerprint_mismatch，界面只给「重新分析」。
  • 成功返回 201 + 新 JobDetail；原 job 任何字段不变。

字段 类型 说明

3.0 信封与陈旧判定

信封最小字段：status（ok | empty | error | stale）、source、as_of、fetched_at、is_stale、error_code、data。完整定义见 Schema。

三条不可混淆的规则：

  1. status = empty：数据源正常响应但今天没有数据（非交易日、板块无成分股、新闻为空）。data = null，error_code = null，as_of = null。
  2. status = error：数据源失败且无法给出可用数据。data = null，error_code 必填（数据源码），as_of = null。
  3. status = stale：有数据但不可信或过期。data 非空，as_of 非空，is_stale = true，stale_reason 必填。

is_stale 恒等于 status == "stale"；保留该布尔字段是为了客户端不必做字符串比较。

as_of 的取值：单区块接口取该块的数据时间；多区块接口取主区块的时间（快照为 quote，市场概览为 indices），主区块不可用时取第一个可用区块。逐块时间始终在 blocks 里，顶层只是给列表和标题用。

多区块接口（快照、市场概览）必须给 blocks，每块独立状态；部分成功用 partial = true 加 failed_blocks 表达，不能用总状态掩盖某一块的失败。合并规则：

各区块状态 顶层 status partial
全部 ok ok false
全部 empty empty false
全部 error error false
至少一个可用（ok/stale），其余 empty 或 error 按可用区块：有 stale 则 stale，否则 ok 有 empty/error 区块时为 true
可用区块里 ok 与 stale 混合 stale 按需

stale_reason 枚举：ttl_exceeded（超过该接口的新鲜度阈值）、trading_day_mismatch（数据日期早于最近交易日）、upstream_fallback（用了备用数据源）。

4. 错误与安全边界

4.1 错误体

非 2xx 响应统一：

{
  "error": {
    "code": "active_conflict",
    "message": "该股票今日已有进行中的分析",
    "request_id": "req_01J...",
    "details": {"active_job_id": "..."}
  }
}

message 是可直接展示给用户的安全文案；details 只放白名单字段（任务 id、字段名、允许值），不放内部异常文本。

4.2 安全规则（实现与测试都按此断言）

  1. 不返回服务端堆栈、异常类名、代码行号。
  2. 不返回任何 API Key、环境变量、内部主机名。
  3. 不返回文件系统路径；下载一律给 /api/v1/... 形式的 URL。
  4. 不接受前端提交 backend_url、api_key、任意模型接口地址；模型与 Base URL 由服务端 llm_profile 白名单决定。
  5. 报告正文与外部文本默认不可信：报告正文按清洗后的 markdown 传递，前端渲染必须禁用原始 HTML；新闻、快讯、题材归因标 data.untrusted = true，按纯文本渲染，不执行脚本、不自动加载外部图片。
  6. 错误响应也带 X-Request-Id，与日志可对账。

4.3 前端不得推断的事项

  • 不解析 sections 文本猜评级、目标价、止损：只用 meta.rating / price_target / stop_reference / time_horizon。
  • 不用 status 自己推按钮：只用 allowed_actions。
  • 不把 empty 当 error，不把 stale 当 ok：三者在信封里是三个值，文案见 semantic-dictionary.md。
  • 不在 SSE 断线时调用创建接口：重连只带 Last-Event-ID（见 sse-events-v1.md）。

SSE 事件流契约 v1

版本：v1（2026-10-29 冻结）

日期：2026-10-29 状态：冻结候选（Day 4 交付） 配套：api-v1.md（JobDetail 字段）、job-state-machine.md（状态与转换）、crash-boundaries.md（B5 补发事件）、error-codes-v1.md

目标：任务页的进度、阶段、统计和完成通知只走一条只读事件流；断线重连只补历史，绝不产生新任务。

1. 端点与握手

GET /api/v1/jobs/{jobId}/events
Accept: text/event-stream
Last-Event-ID: 128        （可选，重连时带）
情况 响应
正常订阅 200，Content-Type: text/event-stream; charset=utf-8，Cache-Control: no-cache，X-Accel-Buffering: no
jobId 不存在 404 job_not_found
用 POST 或其他方法 405 method_not_allowed
Accept 不是事件流 400 invalid_request
Last-Event-ID 非整数 400 invalid_request
游标超出保留窗口 410 sse_cursor_expired（见第 4 节）

一次连接只订阅一个任务，不做多任务复用。P0 无鉴权，跨域默认不开。

2. 帧格式

标准 SSE 帧，data 为单行 JSON：

retry: 3000

id: 128
event: status_changed
data: {"seq":128,"job_id":"5b1c...","type":"status_changed","at":"2026-10-29T10:31:07+08:00","payload":{"from":"running","to":"succeeded","reason":"worker","detail":null,"pending_action":null,"error":null}}

: ping

规则：

  • 每条事件帧的 event 行与 data.type 必须相同；客户端用哪个都行，二者不等即为服务端缺陷。
  • 除心跳外，每条事件的 data 都含五个字段：seq、job_id、type、at、payload。
  • seq 在同一个 job 内从 1 开始严格递增且连续，不跳号、不复用。
  • 心跳是一行注释 : ping，不占 seq，不影响 Last-Event-ID。
  • 服务端在流开始时先发 retry: 3000（毫秒），客户端按此间隔自动重连。

3. 六类事件

type 何时发 载荷
snapshot 连接建立、或重连后需要重建视图时，作为首帧 {job: JobDetail, last_seq: int}
stage_changed 阶段开始、结束、失败、跳过 见 3.1
stats 统计值变化且满足限频；终态前必发一条 见 3.2
status_changed 任何状态转换（T01–T20、对账改判） 见 3.3
report_ready 报告提交成功，紧跟在 succeeded 的 status_changed 之后 见 3.4

created、transition_rejected、reconcile_note 是审计记录，不属于这六类事件。它们只写审计表，不广播、不占 seq。审计记录混进事件流会让序号出现空洞，重连补发就断链。

4. 首帧、续传与保留窗口

4.1 首帧快照

不带 Last-Event-ID 连接时，服务端先发一条 snapshot：

  • payload.job 是完整的 JobDetail（含 12 个阶段），前端据此直接画出进度条与按钮。
  • payload.last_seq 是当前事件表的最大序号，没有事件时为 0。
  • snapshot 的 seq 等于 last_seq，不写入事件表、不推进序号。

4.2 断线续传

带 Last-Event-ID: N 重连：

  1. 服务端从事件表补发 seq > N 的所有事件，顺序按 seq。
  2. 补发完毕再进入实时推送。
  3. 若 N 小于保留窗口内最小序号减一，返回 410 sse_cursor_expired，客户端改用 GET /api/v1/jobs/{jobId} 重建视图。

4.3 保留窗口

  • 每个 job 的事件保留 24 小时，或最近 2000 条，先到者为准。
  • 窗口外的 Last-Event-ID 一律 410，不猜、不跳过、不静默丢事件。
  • 对账补发的事件（如 B5 的 report_ready）在启动时分配新序号追加到尾部，不插入历史位置，因此序号始终连续。

4.4 终态任务的订阅

任务已到终态后再连接：服务端发一条 snapshot 后立即关闭。这是正常结束，不算错误。

5. 心跳与限频

项 规则
心跳 无数据 15 秒发一次 : ping；有心跳不代表任务在推进，只代表连接活着
stats 限频 同一 job 每 2 秒最多一条；期间多次变化合并为最后一条；值没变不发
终态前的 stats 必须发一条最终值，不受限频约束
其他事件 不合并、不丢弃；status_changed 与 stage_changed 必须逐条送达

前端展示「上次更新 x 秒前」用 stats 或心跳时间都行，但不得把心跳当进度。

6. 终态关闭

进入任一终态后，服务端按固定顺序发完再关闭连接：

  1. stats（最终值）
  2. status_changed（到终态）
  3. report_ready（仅 succeeded 且报告已提交）
  4. 关闭连接，不再发心跳

前端收到 EOF 后做一次 GET /api/v1/jobs/{jobId} 校验终态与 report_id，然后停止重连。若 EOF 后连不上，按普通断线处理，重连带 Last-Event-ID。

cancelled / failed / interrupted 不发 report_ready；阶段报告是否可读看 report_id 与报告列表，不在事件流里广播。

7. 重连不得创建任务（硬规则）

以下四条是验收项「SSE 重连没有创建任务语义」的落地条款：

  1. 本端点只有 GET；POST 一律 405。
  2. 订阅与续传只读事件表与 job 表，不写任何行（idempotency-conflicts.md 第 2 节）。
  3. Last-Event-ID 只用于定位事件，不参与任何创建判定。
  4. 410 sse_cursor_expired 的客户端动作固定为：读任务详情，不创建、不重试、不续跑。

实现与测试按「订阅前后 job 表、事件表、报告表行数不变」断言。

错误响应字典 v1

版本：v1（2026-10-29 冻结）

日期：2026-10-29 状态：冻结候选（Day 4 交付） 配套：api-v1.md、market-data-envelope-v1.json

两条出口，不要混用：

  • 接口错误：请求不合法、对象不存在、状态冲突、服务端故障。用 HTTP 4xx/5xx + 错误体。
  • 数据源错误：接口本身正常，但某个数据源取不到数据。用 HTTP 200 + 信封 status = error，error_code 取第 4 节的源码。这样前端能区分「后端坏了」和「这只票今天没数据」。

1. 错误体形状

{
  "error": {
    "code": "active_conflict",
    "message": "该股票今日已有进行中的分析",
    "request_id": "req_01J8Z3K4",
    "details": {"active_job_id": "5b1c..."}
  }
}
字段 必需 规则
code 是 本文件第 2、4 节的枚举值，机器判定用
message 是 可直接展示的中文安全文案；同码文案固定，不做变量拼接以外的拼装
request_id 是 与响应头 X-Request-Id 相同，日志可对账
details 否 白名单字段：对象 id、字段名、允许值、冲突任务 id。禁止异常文本、堆栈、路径、密钥

details 里允许出现的键只有：job_id、report_id、export_id、active_job_id、field、allowed_values、candidates、from、to、rule、retry_after_ms。多一个键即视为契约违规。

2. 接口错误码

code HTTP 触发条件 安全文案 客户端动作
invalid_request 400 JSON 解析失败、类型不对、查询参数取值非法、超出长度上限 请求格式不正确 修请求；不要重试
idempotency_key_required 400 创建任务或重试未带 Idempotency-Key 缺少幂等键 生成 UUID 后重发
method_not_allowed 405 方法不对，如对 SSE 端点发 POST 不支持该请求方法 修调用
job_not_found 404 job id 不存在 没有找到这个任务 回任务列表；不要自动创建
report_not_found 404 report id 不存在 没有找到这份报告 回报告列表
export_not_found 404 export id 不存在 没有找到这个导出任务 重新发起导出
stage_not_found 404 stage id 不在固定 12 个阶段内 没有找到这个阶段 刷新任务详情；按固定阶段列表修正请求

ticker_ambiguous 422 中文名匹配到多只 匹配到多只股票，请选择一只 用 details.candidates 让用户选

3. 状态冲突与转换编号

illegal_transition 的 details.rule 取 job-state-machine.md 的编号：

  • I01–I11：非法状态转换，任何入口一律 409。
  • 合法转换编号为 T01–T20，P1 测试按 p1-state-machine-tests.md 引用。
  • paused → cancelled 直接取消走 I11；合法路径是先走 T20 到 cancel_requested，再由 T13 收尾。
  • 重复提交同一控制动作不算非法转换：返回 200 accepted = false, reason = already_pending（见 api-v1.md 1.6）。

4. 数据源错误码（信封内 error_code）

code 含义 典型来源 顶层 status
upstream_timeout 数据源超时 mootdx / 腾讯 / 东财 / 同花顺 error
upstream_error 数据源返回错误或非预期结构 同上 error
upstream_rate_limited 数据源限流 东财、同花顺 error
data_parse_error 数据源有响应但字段解析失败 腾讯行情、东财资金流 error

四个码都允许出现在区块级（blocks.*.error_code）。顶层 status = error 时顶层 error_code 必填；顶层 status 为 ok / empty / stale 时顶层 error_code 必须为 null，失败信息只留在 blocks 里。

stale_reason 不属于错误码，取值见 api-v1.md 3.0：ttl_exceeded、trading_day_mismatch、upstream_fallback。

5. 不许出现的内容（实现与测试断言）

错误体与信封的任何字符串字段都不得包含：

  1. Python 堆栈特征：Traceback (most recent call last)、File "、line。
  2. 密钥特征：sk-、api_key、Authorization、token=。
  3. 路径特征：Windows 盘符路径、/home/、/Users/、C:\。
  4. 内部主机名或 IP 直连地址。

tests/test_upgrade_market_envelope.py 对五份样本做这四项扫描；服务端实现阶段加同一份断言的集成测试。

9. W09 交易日志不可用

定位：独立应用（默认 http://127.0.0.1:8502），以 iframe 嵌入。本系统不读写它的数据。

可用时：整页 iframe，顶部一行「日志服务运行中」与「新窗口打开」。

不可用时（本线框重点）：

  1. 说明句：「交易日志是独立应用，当前没有在运行。」
  2. 原因按 journal.reason 分支： - not_running：给启动命令 run.bat 与「重试」按钮。 - not_installed：给目录缺失说明与安装指引，不显示启动命令。 - probe_failed：提示端口被其他服务占用，给检查步骤。
  3. 「重试」重新请求 meta/options，不刷新整页。
  4. 声明数据隔离：「本系统不会读取或修改交易日志的数据。」

依赖：GET /meta/options 的 journal 字段。

3. 三层接口

3.1 图层：FakeAnalysisGraph

方法 行为 真实 Runner 对应
prepare_graph_run(ticker, date) 返回初始状态、参数、元信息 TradingAgentsGraph.prepare_graph_run
stream(init_state) 按固定顺序产出 12 个累积状态块 graph.stream(...)
finalize_graph_run(...) 返回三档信号 TradingAgentsGraph.finalize_graph_run

stream 产出的块与真实图同形：分析师阶段给报告键，辩论给 investment_debate_state，风控给 risk_debate_state。

因此同一份流既能喂假执行器，也能喂产品 ProgressTracker，见测试 GF-06。

3.2 执行层：FakeJobRunner

方法 行为
start() T02，queued 到 running，打开阶段流
advance() 跑到下一个阶段边界，最多执行一个阶段
run_all() 从 queued 开始一直跑到终态或 paused
pause() / resume() / cancel() 受理控制请求，按状态机返回 accepted 或抛 IllegalTransition
finalize(cancel_wins=...) 收尾；用于构造 B6 的两种结局
reconcile() 服务重启对账，覆盖 B1 到 B5
job_detail() / snapshot() 生成 JobDetail 与 SSE 首帧
replay(seq) / subscribe(seq) 断线补发与只读重连

控制请求只在阶段边界生效。

调用 pause() 或 cancel() 后再调用 advance()，会在启动下一个阶段之前停住，不会多跑一个阶段。

IllegalTransition 带 rule 字段，P1 把它映射为 HTTP 409 illegal_transition。

3.3 创建层：FakeJobLedger

FakeJobLedger.create() 实现 idempotency-conflicts.md 的五步判定：

  1. 同键同体返回原任务，replayed=True。
  2. 同键异体返回 409 idempotency_mismatch。
  3. 幂等键未命中但同活动指纹存在，返回原任务，existing_header=True。
  4. 同票同日不同配置且有活动任务，返回 409 active_conflict。
  5. 否则创建新任务，返回 201。

第 3 步覆盖首次出现的新键，这样十个不同键的相同请求也只产生一个 job。

账本只在内存里，不模拟数据库事务与唯一索引。

5. 交互与竞争场景

S10 重复启动请求

不进 SCENARIOS 字典，由 GF-18 用 FakeJobLedger 直接构造。

四种情况按 idempotency-conflicts.md 的五步顺序验证：

  1. 同键同体：201 一次，之后 200 重放，replayed=True。
  2. 同票同日同配置、换新键：200 返回原任务，existing_header=True。
  3. 同键异体：409 idempotency_mismatch。
  4. 同票同日不同配置、有活动任务：409 active_conflict，带当前活动任务 id。
  5. 十个不同键同时提交同一意图：只创建 1 个任务，全部返回 job-0001。

第 5 条是并发条款的替身验证：真实系统靠数据库部分唯一索引兜底，假账本靠内存判断。

S11 多浏览器重连

由 GF-19 验证，两个浏览器先后订阅同一任务。

要求：两路首帧逐字段相同；首帧 snapshot 的 seq 等于当前最大序号；订阅前后任务详情、事件条数、序号都不变。

订阅是纯读操作，不创建任务、不推进状态。

S12 事件断线后补发

由 GF-20 验证：跑到第 5 个阶段后记下游标 N，继续跑完，再用 Last-Event-ID: N 重连。

要求：补发的事件恰好是 seq > N 的全部事件，序号从 N+1 连续到当前最大值；首帧仍是 snapshot；用当前最大序号重连时补发为空。

3. 八项指标

编号 名称 测什么 通过线来源
P01 冷启动 进程冷启动到首屏可交互 基线 +10%
P02 路由切换 页签之间切换的耗时 基线 +10%
P03 报告 GET 打开一份已生成报告的耗时 首次测量后定基线
P04 报告列表筛选 按股票、日期、状态筛选的响应耗时 首次测量后定基线
P05 任务事件延迟 事件产生到界面可见；以及阶段间隔偏差 事件 ≤ 500ms，阶段偏差 ≤ 5%
P06 PDF 首次生成 无缓存时导出 PDF 的耗时 设计目标 ≤ 8 秒
P07 PDF 缓存命中 同内容重复导出的耗时 设计目标 ≤ 300ms
P08 移动视口溢出和交互耗时 390x844 下是否横向溢出、点击到响应的耗时 零溢出；交互基线 +10%

P01 冷启动

三个观测点：

  1. 进程启动到启动遮罩放行（data-boot-gone 变为 1）。
  2. 遮罩放行到首屏静默（含 2 秒静默窗）。
  3. 移动视口重复一次首屏。

旧版基线：遮罩放行 2.47 秒，桌面首屏 5.74 秒，移动首屏 6.26 秒。

新版首屏是任务列表页，不是旧版分析页，因此 5.74 与 6.26 只作量级参照，判定以「新版连续五次的波动范围」加「不劣于旧版同量级」双条件为准。

P02 路由切换

至少四个方向：任务列表到任务详情、详情到报告、报告到历史列表、历史列表回任务列表。

缓存状态要分开记：冷切换（首次进入，需请求数据）与暖切换（缓存命中）。

旧版基线可对标的是旧页签切换：冷 4.34 秒，暖 2.00 到 2.31 秒。

P03 报告 GET

起点：报告列表点击某一行。终点：正文首段可见且图表占位消失。

必须使用已生成的报告，不触发 PDF、不触发外部行情。

记录三种情况：报告在首屏（小报告）、需要滚动（长报告）、历史导入报告（无图表快照）。

P04 报告列表筛选

分别记录：单条件（股票代码）、双条件（日期区间加状态）、空结果。

空结果也要测：它最容易暴露前端把「无数据」渲染成无限加载。

P05 任务事件延迟

两个子项：

  1. 事件延迟：服务端写入 stage_changed 或 status_changed 的时间戳，到界面出现对应变化的间隔。上限 500ms。
  2. 阶段间隔：相邻两个 stage_changed（前一阶段 done 到后一阶段 started）的时间差，与阶段真实耗时对比。偏差超过 5% 说明前端或事件通道在积压。

阶段间隔只能用真实任务或录制回放测，不能用假图的虚拟时长。

假图的 30 分钟是设定值，不是性能数据。

P06 PDF 首次生成

清空导出缓存后导出一次，记录总耗时与文件大小。

必须记录报告 id、content_hash、导出器版本，三者构成缓存键。

P07 PDF 缓存命中

同一报告、同一内容哈希、同一导出器版本再导出一次。

只允许读缓存，不得重新渲染。

若耗时接近 P06，说明缓存键没生效，按缺陷处理而不是按性能问题处理。

P08 移动视口溢出和交互耗时

两项独立判定：

  1. 溢出：每个页面执行 document.documentElement.scrollWidth <= clientWidth，任一页为假即失败。
  2. 交互：移动端点击主要按钮（开始分析、暂停、取消、打开报告）到界面响应的耗时，记录中位数。

溢出是硬失败，不接受「只溢出几个像素」。

4. 结果记录格式

结果写入 perf-result-template.json 的副本，文件名 perf-result-<日期>-<序号>.json。

字段规则：

字段 规则
schema_version 固定 perf-result-v1
run.commit 被测代码的短哈希，不许填 HEAD
run.date 采集日期，不是提交日期
method 照抄第 2 节，改了任何一项都要在 notes 写明
metrics.P01 到 P08 八项齐全，缺项填 null 并在 notes 写原因
samples 毫秒整数数组，至少 5 个；布尔项用 0 或 1 之外的显式字段
median 由 samples 计算，不手填
budget 通过线；无基线的新指标填 null 并写 budget_source
pass median <= budget 为真；无预算时为 null
regressions 未达标项列表，空数组表示全过
verdict pass / fail / baseline_only

禁止事项：

  • 不把假图或模拟器的虚拟时长填进任何指标。
  • 不用单次样本代替五次中位数。
  • 不混用不同脚本或不同静默窗的数字。
  • 不在 notes 里写「感觉更快」这类无数据结论。
