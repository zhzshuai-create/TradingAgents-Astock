## 四、契约行为

依据：`contracts/sse-events-v1.md` 全文、`contracts/api-v1.md` 第 2.6 与 266 行、`contracts/core-wireframes.md` 第 4 节 W04、`contracts/interaction-checklist.md` A05/A06。

### 4.1 握手与传输

- `GET /api/v1/jobs/{jobId}/events`，请求头 `Accept: text/event-stream`，重连可带 `Last-Event-ID: <整数>`。
- 正常 200 为 `text/event-stream; charset=utf-8`、`Cache-Control: no-cache`、`X-Accel-Buffering: no`。
- 404 `job_not_found`、405 `method_not_allowed`、400 `invalid_request`、410 `sse_cursor_expired` 都是 JSON 错误体，交给现有 `toApiError` 语义处理。
- 原生 `EventSource` 无法在新页面加载时手动设置 `Last-Event-ID` 头，所以用 `fetch` + `AbortController` + `ReadableStream` 自己解析；`fetch` 与 `/api/v1` 字面量只能出现在 `frontend/src/api/`，由 `client.test.ts` 的 URL 归属守卫继续守护。
- 流结束（EOF）不等于终态：只有任务进入终态后的 EOF 才停止重连，其他 EOF 按断线重试。

### 4.2 帧格式

- 标准 SSE：`retry:`、`id:`、`event:`、`data:`、注释行（`: ping`）与空行分隔。
- `data` 是单行 JSON；多行 `data:` 按换行拼接。注释与 `retry:` 不进入事件，也不要让服务端的 `retry: 3000` 覆盖本票规定的 1/2/4/8 秒退避。
- 除心跳外，每条 `data` 都有 `seq`、`job_id`、`type`、`at`、`payload`；帧的 `event` 行必须与 `data.type` 相同，不同视为协议错误，停止连接并按一次详情重建处理。
- `seq` 在同一任务内从 1 严格递增。应用一条事件后游标取 `max(当前游标, seq)`；`seq <= 已应用游标` 的帧直接丢弃。
- 心跳只证明连接活着，不改阶段与进度，也不能被当成「有新事件」。

### 4.3 首帧、刷新与续传

- 不带游标连接：首帧 `snapshot`，`payload = {job: JobDetail, last_seq}`；直接用 `job` 覆盖详情缓存，把 `last_seq` 写入游标。
- 带游标连接：服务端仍先发 `snapshot`（当前完整 JobDetail，`last_seq` 为当前最大 seq），再补发 `seq > 游标` 的历史帧。由于快照已经把状态推到最新，补发帧的 seq 通常小于等于 `snapshot.payload.last_seq`；客户端按 4.2 单调丢弃，绝不能让补发把界面拉回旧状态。
- 刷新页面：P2-10 的详情 GET 先重建页面，事件流带 `sessionStorage` 里的游标续传；A05 断言刷新后阶段与按钮一致、任务数不变。
- 游标按 jobId 分开存 `sessionStorage`（如 `ta:job-cursor:<jobId>`），读写都包 try/catch，存储不可用时退化为无游标快照。
- 终态连接关闭并完成最终详情校验后清掉该任务的游标；下一个任务不能复用上一个任务的游标。
- 保留窗口是每个任务 24 小时或最近 2000 条，先到者为准；游标落在窗口外只会得到 410。

### 4.4 六类事件如何落到界面

| 事件 | 处理 |
| --- | --- |
| `snapshot` | `payload.job` 整体替换详情缓存；游标取 `payload.last_seq`；界面按九状态与 12 阶段重画 |
| `stage_changed` | `stage_status = started` 时该阶段置 `active` 并写 `started_at`；`done`/`failed`/`skipped` 时置同名状态并写 `finished_at`、`duration_ms`；名称与序号以载荷为准，不按数组位置猜 |
| `stats` | 整体替换 `job.stats` 四项；值没变也要按帧应用，界面不额外抖动 |
| `status_changed` | 更新 `status`、`pending_action`、`error`；`allowed_actions` 不在载荷里，不得在前端推状态表，终态时用一次详情 GET 校准 |
| `report_ready` | 写 `report_id`，让头部的「打开报告」出现；不打开阅读器、不解析报告正文 |
| `error` | `payload.fatal = true` 时停止连接并做一次详情 GET 重建；`fatal = false` 不重连，保留现有界面 |

- 终态判定只用 `succeeded`、`failed`、`cancelled`、`interrupted`。进入终态后按契约顺序收完 `stats`、`status_changed`、`report_ready`，EOF 后做一次 `GET /api/v1/jobs/{jobId}` 校验终态与 `report_id`，然后停止重连并清游标。
- 非终态 EOF 或网络错误：保留现有数据，显示黄条并重试。
- P2-10 的「最近完成阶段自动展开一次」保持不变；SSE 更新阶段状态不重新自动展开，避免用户正在看的报告被抢走。

### 4.5 黄条与 410

- 断线重试期间，详情顶部显示黄条「正在重连，阶段可能延迟」；连接成功（200）或收到首帧后自动消失。黄条用 `role="status"` 与 `aria-live="polite"`，不是对话框，不抢焦点。
- 410 `sse_cursor_expired`：清掉该任务游标，停止自动重连，黄条改为「刷新以恢复」并给刷新按钮；不重放旧事件、不创建任务、不续跑。
- 刷新按钮执行整页刷新或等价的详情重建；重建后没有游标，从 `snapshot` 重新开始。
- 黄条在 390/360 不遮挡底部导航，不引入横向滚动。

### 4.6 退避与终态关闭

- 重试间隔固定 1 秒、2 秒、4 秒、8 秒，之后保持 8 秒；任一次连接建立成功即重置为 1 秒。
- 页面卸载、切换 jobId、进入终态、410 都要取消当前请求、清掉定时器并释放 `AbortController`；React StrictMode 下 effect 会执行两次，不得留下两条并发连接。
- 终态后不再新建连接；服务端在终态按顺序发完并关闭是正常结束，不算错误。

### 4.7 只读

- 本票只有 `GET /events` 与终态校准的 `GET /jobs/{id}`；不得调用 `POST /jobs`、`POST /actions`、`POST /retry`。
- A05/A06 断言订阅前后任务数不变、浏览器写请求为空；重连、410、刷新都不创建任务。

## 八、必须守的约束

- 只有 GET；订阅、重连、410 与刷新都不得创建任务或调用控制接口。
- 事件流请求只能写在 `frontend/src/api/sse.ts`，组件不直接 `fetch`，不写 `/api/v1` 字面量。
- 原生 `EventSource` 不能满足刷新后续传的请求头要求，使用 fetch 流并自行解析；不要为此新增后端查询参数。
- 游标按 jobId 存 `sessionStorage`，只进 `Last-Event-ID` 头，不进 URL、不进日志。
- 退避固定 1/2/4/8 秒，忽略服务端 `retry:` 行；连接成功重置。
- 410 只做「刷新以恢复」，不重放旧游标、不自动重试。
- `snapshot` 是权威状态；补发的旧帧按 seq 单调丢弃，不能让界面回退。
- `allowed_actions` 只来自服务端；事件载荷没有它，终态用详情 GET 校准，不在前端推状态表。
- 九状态与阶段文案继续用共享词汇；`interrupted` 仍是「等待人工处理」，任何地方不得写成「运行中 / 进行中」。
- 黄条是 `role="status"` 的顶部提示，不抢焦点；390/360 不遮挡底栏、不横向溢出。
- 终态后停止重连；非终态 EOF 才重试。
- 一票一本地提交，不推送；存档单独提交。

## 九、容易踩的坑

1. `EventSource` 不能设置请求头：页面刷新后无法手动带 `Last-Event-ID`，必须用 fetch 流；这同时满足「fetch 只在 api/」的守卫。
2. 响应体可能按任意字节切块，中文和 emoji 会跨 chunk；用 `TextDecoder` 的流式模式，不要每次 `decode` 都新建解码器。
3. 事件之间用空行分隔，最后可能没有空行；流结束时把缓冲区里剩下的完整帧处理完。
4. 后端带游标时仍先发 `snapshot` 再补发历史；补发帧的 seq 小于快照的 `last_seq`，必须丢弃旧帧，否则界面会倒退。
5. 心跳 `: ping` 不占 seq，不要写游标，也不要当进度更新。
6. 410 的响应是 JSON 错误体而不是事件流；先看状态码再判断 `content-type`，不要把它当协议错误反复重连。
7. 终态关闭后 `report_ready` 可能紧跟在 `status_changed` 后面；EOF 校准用一次详情 GET 兜底，防止漏掉 `report_id`。
8. `status_changed` 不带 `allowed_actions`；不要复制一份状态表到前端。P2-11 只在终态校准一次详情，不在每次状态变化时 GET。
9. `snapshot` 整体替换详情会重建阶段数组；P2-10 的自动展开只按 jobId 触发一次，不要因事件更新再次自动展开。
10. 切换 jobId 要清掉旧连接、定时器和游标，避免上一个任务的帧写进新页面缓存。
11. React StrictMode 的 effect 双执行会开两条连接；用 ref 保存 `AbortController`，清理函数里 abort 并置空。
12. 退避定时器在组件卸载后仍可能触发重连；定时器与连接都要在清理函数里取消。
13. `retry: 3000` 是服务端建议值，但验收要求 1/2/4/8 秒；不要把它写进重试逻辑。
14. 刷新按钮触发的整页重建不能再带旧游标；410 分支必须先删游标。
15. 详情 GET 与 snapshot 会并发返回；以 seq 较大或后到的权威快照为准，不要让旧 GET 覆盖新 snapshot。
16. Shell E2E 的 `/api/v1/jobs**` 通配桩会截住 `/events`；必须注册更具体的 `/api/v1/jobs/job-1/events`，返回 `text/event-stream` 的 snapshot 帧后关闭。
17. `--no-worker` 的 dev 后端不会产生新事件；A05/A06 需要真实 Worker 与假图推进，`--stage-delay-ms` 只用于放慢阶段边界。
18. Playwright 的 `context.set_offline` 会连页面资源一起断；断事件流只用路由 abort。
19. 事件流是只读的：即使 `status_changed` 到 `paused`，也不要在这里发 resume 请求；控制动作属于 P2-12。
20. TypeScript 严格模式会拒绝未使用的参数与变量；解析器的中间变量与事件类型要收干净。
