# AStock Pro P0「基线与契约」逐日实施计划

日期：2026-10-28  
对应总计划：P0 基线与契约  
建议工期：7 个工作日 + 1 个缓冲日  
实施目标：让后续前后端开发有稳定依据，不再边写页面边猜任务、报告和数据结构

---

## 先说结论

P0 不建设正式新版页面。

P0 也不改多智能体分析逻辑。

P0 只完成四件事：

1. 冻结一个可恢复、可测试的旧版基线。
2. 固定任务、报告、接口和数据状态契约。
3. 准备不调用真实模型的测试样本与假图。
4. 确认核心页面线框和 P1 开发边界。

P0 最重要的交付不是文档数量，而是消除关键歧义。

后续开发者拿到契约后，应该能够直接回答：一个任务何时算开始、何时算暂停、刷新后如何恢复、重跑是否覆盖报告、空数据和接口失败如何区分。

# 二、每日共同规则

## 2.1 每日开始

- 查看当天任务和前一天未解决项。
- 记录当前工作树状态。
- 确认当天不会触发真实模型。
- 只打开当天需要的文件，避免顺手扩大改造范围。

## 2.2 每日结束

- 更新当天交付和验收结果。
- 将文档、样本和测试分别整理成可审查的小改动。
- 记录尚未决定的契约问题，不能口头带过。
- 旧版仍需能够启动，已有测试不得被无意破坏。
- 长文档同时提供可阅读的 HTML 版本。

## 2.3 提交边界

每天的工作应能独立审查和回退。

基线文档、任务契约、报告契约、接口契约、测试样本和假图不混成一个大提交。

涉及提交、标签、推送和物理备份时，按用户确认后的命令执行，不在计划中默认擅自操作。

# 三、Day 1：冻结旧版与恢复基线

## 当日目标

确认“现在正在运行的旧版到底是什么”，并保证后续任何时候都能恢复。

## 3.1 仓库基线

需要记录：

- 当前分支和 HEAD。
- 最近关键提交。
- 已跟踪文件的未提交修改。
- 未跟踪文件。
- 当前 Python 和关键依赖版本。
- 主平台与交易日志的启动方式。
- 当前使用的端口和配置项。

重点检查此前已经存在的前端、数据和测试修改。

不得把已有未提交工作直接当成新版 P0 改动。

## 3.2 旧版测试基线

执行并记录：

- `pytest -q`。
- `ruff check .`。
- `git diff --check`。
- 现有 Streamlit AppTest。
- 现有浏览器启动验收脚本。

如果存在失败或跳过，逐项记录原因。

不得为了让基线好看而删除测试或隐藏失败。

## 3.3 数据与恢复基线

盘点并备份：

- `~/.tradingagents/logs/`。
- `~/.tradingagents/incomplete_tasks.json`。
- `~/.tradingagents/cache/checkpoints/`。
- 非敏感模型配置。
- 数据库或缓存目录的实际位置。

恢复方案至少包括：

- 一个可识别的代码恢复点。
- 一份当前未提交补丁。
- 一份独立物理副本。
- 一份数据目录备份。
- 一份恢复操作说明。

## 3.4 旧版功能与性能基线

使用模拟报告和现有页面完成：

- 首页截图。
- 市场看板截图。
- 任务运行页截图。
- 报告页截图。
- 交易日志集成截图。
- 1440 × 1000、390 × 844、360 × 800 三种视口。
- 冷启动、页面切换和报告打开耗时。
- 浏览器 console 与 pageerror 记录。

## 当日交付

- `repository-baseline.md`。
- `test-baseline.md`。
- `performance-baseline.md`。
- `recovery-baseline.md`。
- 基线截图与结构化浏览器结果。
- 恢复点和备份的位置清单。

## 当日验收

- 能明确说明当前旧版对应的代码和未提交补丁。
- 能明确说明测试通过数、跳过数和已有失败。
- 能按文档恢复旧版代码和数据。
- 没有触发真实模型。
- 没有修改核心分析逻辑。

## 阻塞时怎么处理

如果旧版测试本身不稳定，先记录并隔离问题。

不要在 P0 顺手进行大规模修复。

只有阻止后续契约测试的旧版缺陷，才单独立项修复。

# 四、Day 2：冻结任务语义、状态机与幂等规则

## 当日目标

让任务控制不再依赖页面文案猜测真实状态。

这是 P0 最重要的一天。

## 4.1 建立核心语义词典

至少统一以下词语：

- 新建分析。
- 重新分析。
- 重试。
- 从检查点继续。
- 暂停中。
- 已暂停。
- 取消中。
- 已取消。
- 连接中断。
- 执行中断。
- 已完成。
- 已失败。

每个词都要写清楚：用户看到什么、服务端实际做什么、是否可能产生模型费用。

## 4.2 固定任务状态

首期状态限定为：

```text
queued
running
pause_requested
paused
cancel_requested
cancelled
succeeded
failed
interrupted
```

为每个状态定义：

- 是否占用 Worker。
- 是否允许暂停。
- 是否允许恢复。
- 是否允许取消。
- 是否允许重试。
- 是否可以有报告。
- 浏览器刷新后如何展示。
- 服务重启后如何展示。

## 4.3 画出合法状态转换

必须覆盖：

- 创建后排队。
- Worker 认领后运行。
- 正常完成。
- 执行异常。
- 暂停请求与确认。
- 暂停后恢复。
- 取消请求与确认。
- Worker 租约失效。
- 中断后人工续跑。
- 中断后重新分析。

非法转换也要明确，例如：

- 已成功任务不能直接变回运行。
- 已取消任务不能自动重新排队。
- 已失败任务不能覆盖原任务重试。
- 重试必须生成新任务 ID。

## 4.4 固定幂等与冲突规则

需要写清：

- 相同幂等键、相同请求体返回原任务。
- 相同幂等键、不同请求体返回冲突。
- 相同活动配置指纹返回已有任务。
- 同股票、同日期、不同配置的活动任务返回冲突。
- 打开任务 URL 不创建任务。
- 刷新页面不创建任务。
- SSE 重连不创建任务。
- 查看历史报告不停止任务。
- 中断任务不自动重放。

## 4.5 定义最难的崩溃边界

逐项给出预期结果：

1. 任务已创建，Worker 尚未开始。
2. 图已开始，尚无阶段报告。
3. 阶段已完成，事件尚未保存。
4. 核心报告已落盘，应用数据库尚未提交。
5. 报告已提交，完成事件尚未发送。
6. 用户请求取消时，图正在完成收尾。

这里不能承诺绝对无损。

无法确认执行位置时，预期结果应是 `interrupted` 和人工对账，而不是自动重跑。

## 当日交付

- `semantic-dictionary.md`。
- `job-state-machine.md`。
- 状态转换表。
- 幂等与冲突决策表。
- 崩溃边界预期表。
- P1 状态机测试用例清单。

## 当日验收

- 任意一个用户操作都能对应唯一的服务端语义。
- “重试”和“续跑”不再混用。
- 所有终态都有防重启规则。
- 所有可能付费的中断场景都默认禁止自动重放。
- 前后端对同一状态使用同一中文文案。

# 五、Day 3：冻结报告结构与黄金样本

## 当日目标

保证刚完成报告、历史报告、网页、Markdown 和 PDF 使用同一份内容。

## 5.1 盘点现有报告字段

对照以下路径：

- 运行完成状态。
- 核心报告落盘。
- 历史文件读取。
- 报告阅读器。
- Markdown 导出。
- PDF 导出。

列出每个字段的来源、别名、是否必需和缺失时表现。

特别检查：

- `trader_investment_plan` 与 `trader_investment_decision`。
- `data_quality_summary`。
- 五档信号。
- 七类分析师报告。
- 多空辩论。
- 风控决策。
- 最终决策。
- 目标价、止损和时间范围。

## 5.2 定义报告元数据

至少包括：

- `report_id`。
- 可空 `job_id`。
- 股票代码和名称。
- 分析日期。
- 实际生成时间。
- 报告来源：新版或旧版导入。
- 规范结构版本。
- 内容哈希。
- 配置摘要。
- 数据质量状态。
- 图表数据快照状态。
- 重试来源任务。

旧报告没有真实生成时间时，不用文件修改时间冒充。

## 5.3 定义报告正文结构

每章使用稳定的章节 ID、顺序、标题和正文。

前端不能依赖数组下标猜测章节。

缺失章节显示“—”或不展示，但规则必须统一。

长报告不得静默截断。

## 5.4 定义版本与导出规则

- 每次成功分析生成新 `report_id`。
- 重跑不覆盖旧报告。
- 同股票同日期允许多版本。
- 网页、Markdown 和 PDF 使用同一规范结构。
- 打开报告不生成 PDF。
- 打开报告不请求外部行情。
- 新版报告尽量冻结图表输入。
- 旧报告补数导出必须标注补数时间。

## 5.5 准备黄金样本

至少准备：

1. 完整新版 final state。
2. 完整旧版历史 JSON。
3. 缺少可选字段的报告。
4. 超长报告。
5. 包含五档信号的样本。
6. 包含外部文本和 HTML 字符的安全样本。

黄金样本必须可读、可版本管理，不包含 API Key 和个人敏感数据。

## 当日交付

- `report-schema-v1.md`。
- `report-schema-v1.json`。
- `final_state_v1.json`。
- `legacy_report_v1.json`。
- `missing_fields_report.json`。
- `long_report.json`。
- 报告字段新旧对照表。
- 报告一致性测试清单。

## 当日验收

- 同一黄金样本可以明确表示网页、Markdown 和 PDF 的预期内容。
- 新旧字段别名有唯一归一化结果。
- 缺失字段不会导致前端编造数据。
- 同股票同日期两个版本可以同时存在。
- 样本中不存在真实密钥和个人数据。

# 六、Day 4：冻结 API、SSE 与数据状态契约

## 当日目标

让前后端可以独立开发，不让 React 直接理解 Python 私有对象。

## 6.1 固定任务接口

定义以下接口的请求、响应和错误：

```text
POST /api/v1/jobs
GET /api/v1/jobs
GET /api/v1/jobs/{jobId}
POST /api/v1/jobs/{jobId}/actions
POST /api/v1/jobs/{jobId}/retry
GET /api/v1/jobs/{jobId}/events
```

明确创建任务需要 `Idempotency-Key`。

明确控制接口是异步请求，不代表操作已经立即完成。

## 6.2 固定报告接口

```text
GET /api/v1/reports
GET /api/v1/reports/{reportId}
GET /api/v1/reports/{reportId}/markdown
POST /api/v1/reports/{reportId}/exports/pdf
```

在契约中明确：报告 GET 没有 PDF、行情和写文件副作用。

## 6.3 固定市场与股票接口

覆盖：

- 股票搜索。
- 股票快照。
- K 线和分时。
- 股票新闻。
- 股票报告。
- 市场概览。
- 行业。
- 强势股。
- 资金流。
- 快讯。

不需要在 P0 实现这些接口，但必须固定返回结构和错误语义。

## 6.4 固定统一数据状态

市场数据至少返回：

```text
status: ok | empty | error | stale
source
as_of
fetched_at
is_stale
error_code
data
```

分别准备正常、空、失败和陈旧样本。

“部分成功”需要表达区块级状态，不能用一个总状态掩盖所有失败。

## 6.5 固定 SSE 事件

至少定义：

- `snapshot`。
- `stage_changed`。
- `stats`。
- `status_changed`。
- `report_ready`。
- `error`。

每个事件需要序号、任务 ID、类型、时间和载荷。

明确首次快照、断线续传、心跳、终态关闭和统计限频。

## 6.6 固定错误与安全边界

- 错误响应包含安全消息和请求 ID。
- 不把服务端堆栈返回浏览器。
- 不返回 API Key。
- 不返回任意文件路径。
- 不允许前端提交任意服务端配置。
- Base URL 使用服务端允许范围。
- 报告和外部文本默认不可信。

## 当日交付

- `api-v1.md`。
- `sse-events-v1.md`。
- `market-data-envelope-v1.json`。
- `market_empty.json`。
- `market_error.json`。
- `market_stale.json`。
- 错误响应字典。
- 前后端契约评审记录。

## 当日验收

- 前端不需要读取 LangGraph 原始对象即可完成页面设计。
- 所有付费动作都有幂等规则。
- 所有报告读取接口都明确无副作用。
- 空数据、错误和陈旧三种响应不可混淆。
- SSE 重连没有创建任务的语义。

# 八、Day 6：准备确定性假图与验收工具

## 当日目标

让 P1 可以在不调用真实模型的情况下测试任务全生命周期。

## 8.1 假图的基本能力

假图需要提供与真实 Runner 相近的执行接口，但内部使用固定样本。

至少支持：

- 按固定顺序产生十二阶段。
- 返回完整状态块。
- 产生调用和 Token 统计。
- 生成最终黄金报告。
- 人为控制每个阶段等待时间。
- 在安全边界响应暂停和取消。
- 在指定阶段抛出异常。
- 在指定阶段模拟进程中断。

## 8.2 假图必须确定性

相同输入应产生相同事件顺序和报告内容。

不访问真实模型。

不访问真实行情。

不写真实用户报告目录。

不依赖随机睡眠造成不稳定测试。

## 8.3 崩溃与竞争场景

至少预留：

- 创建后立即取消。
- 运行中暂停。
- 暂停后取消。
- 阶段完成后异常。
- 最终报告前中断。
- 最终报告后、数据库提交前中断。
- 重复启动请求。
- 多浏览器重连。
- 事件断线后补发。

P0 只要求假图和场景准备，不要求 P1 数据库实现已经通过。

## 8.4 建立测试矩阵映射

每个 P1 测试需要关联：

- 对应契约条款。
- 使用的样本。
- 操作步骤。
- 预期状态。
- 预期事件。
- 预期模型调用次数。
- 预期报告结果。

## 8.5 完成性能测量模板

固定以下指标的记录格式：

- 冷启动。
- 路由切换。
- 报告 GET。
- 报告列表筛选。
- 任务事件延迟。
- PDF 首次生成。
- PDF 缓存命中。
- 移动视口溢出和交互耗时。

## 当日交付

- `fake_analysis_graph.py`。
- 假图使用说明。
- 崩溃与竞争场景清单。
- 契约到测试的映射表。
- 性能测量模板。
- 不访问真实网络的验证结果。

## 当日验收

- 假图可以重复产生一致结果。
- 可以人为指定失败和中断位置。
- 默认测试路径没有真实模型和真实行情请求。
- P1 的核心任务风险都有对应测试场景。

# 九、Day 7：契约冻结、评审与 P1 拆票

## 当日目标

确认 P0 已足够稳定，可以进入持久化任务内核开发。

## 9.1 交叉检查契约

重点检查：

- 任务状态与接口状态一致。
- 任务状态与线框文案一致。
- 报告结构与黄金样本一致。
- 报告 ID 与重试关系一致。
- 数据状态与市场线框一致。
- SSE 事件与任务状态机一致。
- 错误响应与页面下一步操作一致。

发现冲突时，以真实执行语义为依据修改，不为了页面好看而掩盖状态。

## 9.2 冻结契约版本

为首版契约标记 `v1`。

记录后续允许的变化：

- 新增可选字段可以兼容。
- 修改字段含义需要升级版本。
- 删除字段需要评审。
- 状态机新增状态需要同步前端和测试。
- 报告结构变化需要同步黄金样本。

## 9.3 把 P1 拆成独立任务

建议拆成：

1. SQLite 与迁移基础。
2. 任务表、阶段表和事件表。
3. 配置快照和配置哈希。
4. 创建任务与幂等。
5. Worker 单行租约。
6. 假图执行适配。
7. 阶段保存与统计事件。
8. 暂停、恢复和取消。
9. 终态与重试。
10. 崩溃检测和 `interrupted`。
11. SSE 快照、事件和重连。
12. 旧新 Runner 黄金样本对照。
13. 任务内核性能与故障测试。

每个任务写清依赖、涉及文件、测试和回退方式。

## 9.4 做 Go / No-Go 评审

只有全部通过才进入 P1：

- 旧版可恢复。
- 契约没有关键空白。
- 黄金样本可用。
- 假图可用。
- 主流程线框已走查。
- P1 任务可以独立验收。
- 真实模型仍然默认禁用。

## 当日交付

- `p0-exit-review.md`。
- `p1-backlog.md`。
- 冻结后的契约文件。
- P0 验收证据索引。
- P1 实施顺序和依赖图。

## 当日验收

- 评审结论明确为 Go 或 No-Go。
- No-Go 项有负责人、动作和预计解决时间。
- P1 不需要重新讨论已经冻结的基础语义。

# 十二、P0 最容易失控的地方

## 把写文档变成形式

如果契约没有状态转换、字段样本和异常预期，文档再多也不能指导开发。

验收时必须拿具体操作逐条走，而不是只检查文件是否存在。

## 在 P0 顺手做正式前端

正式 React 会迅速扩大范围。

P0 只做线框和交互走查，避免任务语义尚未固定就投入页面开发。

## 用真实模型验证

真实模型会增加费用和不确定性。

P0 全部使用黄金样本和假图。

真实模型只留到新版任务内核通过后的 Canary。

## 忽略当前未提交工作

当前工作树已经有旧版优化和测试修改。

如果不先记录，后续恢复标签无法完整代表用户正在使用的版本。

## 把检查点当成万能恢复

检查点必须匹配配置和图版本。

无法确认兼容时，只能重新分析，不能自动续跑。
